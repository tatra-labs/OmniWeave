# Repository Layout, Packaging and Release Engineering

## In one paragraph

One repository, one `uv` workspace, one `uv.lock`, one `RELEASE` tag, fourteen `py3-none-any`
distributions built on one runner, and exactly two languages — Python everywhere and TypeScript only
inside `toolchains/`, which no `pip install` can reach. The physical shape enforces the logical one:
`omniweave-ports` has an empty `dependencies` list, `omniweave-core` has exactly one entry in its,
and a gate reads each distribution's entry points to derive the `tools/layers.toml` row it is allowed
to have, so no author picks their own. Versioning runs on the charter's three axes (`RELEASE`,
`CONTRACT`, `SCHEMA`) plus the on-disk versions that move independently of the software; nothing
invents a fourth. CI is two workflow files, thirty numbered gates, nine unnumbered job
assertions, nineteen PR jobs and a release path that signs SBOMs, emits SLSA provenance and publishes
through PyPI Trusted Publishing from the same run that ran the gates — which is why there is no
`repository_dispatch` anywhere in it.

This document owns the repository tree, every `pyproject.toml`'s contents, the install profiles and
their weights, the CI job graph, the release artefacts and the conventions. It does not own the
component responsibilities ([system architecture](02-architecture.md) §2), the stability-tier
vocabulary ([system architecture](02-architecture.md) §2), the import-rule enforcement mechanisms
([system architecture](02-architecture.md) §3.3), the L2 schema-evolution table ([the document
model](03-document-model.md) §15), the store's schema-compatibility table and `migration` DDL
([storage and retrieval](07-store-and-retrieval.md) §3.1, §3.8), the driver-side card and lockfile
grammars ([the driver system](04-driver-system.md) §4.1, §5.5), the `ActionSpec` registry and the CLI
verb tree ([interfaces](10-interfaces.md)) or the gate/counter/budget semantics and the eval pyramid
([quality](13-quality.md)). It states the contract it depends on and links.

Four root-level facts that are load-bearing rather than tidy:

1. **`release.yml` must never be renamed.** PyPI Trusted Publishing binds the OIDC subject to
   `repository` + `workflow_ref`, so a rename silently revokes publish rights and the failure appears
   only at the publish step of a tagged release. The filename is asserted by a gate (§7.3) so a
   rename fails on the PR that does it, not four weeks later on the tag.
2. **`NOTICE`, `LICENSES/` and `THIRD_PARTY.md` are generated, per distribution, and `--check`
   gated.** Attribution drift is the single most common licence defect in the mined collection.
   codegraph vendors 27 tree-sitter grammars as `.wasm` at pinned revisions (66 MB), with sha
   comments in `Cargo.toml` and a `kernel-grammar-parity` test asserting node-kind-table equality —
   genuinely careful supply-chain work — and ships **three** `LICENSE` files among the 27, no
   top-level `NOTICE` and no `THIRD_PARTY`, leaving it plausibly out of compliance with ~24 upstream
   MIT grammar licences whose text MIT requires be shipped with "substantial portions". hyperframes
   packs ≈212 MB of third-party binaries into a Lambda zip (Chromium 70 MB + ffmpeg 80 MB +
   ffprobe 62 MB), asserts the *architecture* of the ffmpeg binary
   (`packages/aws-lambda/scripts/build-zip.ts:414`) but not its hash, and carries no ffmpeg
   attribution anywhere in `packages/aws-lambda/` — while demonstrably knowing the practice, since
   `skills/talking-head-recut/NOTICE.md` attributes the skill it was adapted from. Both are otherwise
   disciplined repositories. Generating the files is the only defence that survives a rush; §9.1 says
   why there are sixteen copies of them and not one.
3. **`.gitignore` must exclude `*.owstore`.** A tracked store is a corpus committed to git — it
   fails `ow doctor` with `OW-S-060` at runtime (00-vision V01-16), and `.gitignore` is what stops it
   reaching a PR at all.
4. **`uv.lock` is committed and never shipped.** It is the reproducibility basis of CI and of every
   golden; it is not in any wheel, is not a cache-key input for a *driver* (charter F26 owns that
   question), and it does not describe what a consumer will resolve. §6.6's wheelhouse install is
   what tests the metadata a consumer actually resolves against. It *is* a CI cache-key input, and
   §4.2 counts what that costs on a release commit.

### 1.2 `packages/` — the fourteen distributions

One box is one wheel. `deps` is complete, first-party edges included, because a reader who cannot see
the first-party edge cannot check `tools/layers.toml` against this table. `tier` is one of the five
stability tiers defined in [system architecture](02-architecture.md) §2 and means the promise the
*distribution's public surface* makes, not the promise of every module inside it. `ceiling` is the
`tools/weights.toml` row in megabytes — the **marginal** installed size, meaning this distribution's
own files plus the third-party closure it introduces, excluding first-party siblings, which are
counted in their own rows. §2.5 shows why that is the only self-consistent reading of the column.

**Why the ports/core split is physical and not stylistic.** `omniweave-ports` is the only
distribution with an empty `dependencies` list, and it is versioned by **Port major** rather than by
`RELEASE` — the one exception to "one `RELEASE`", and the whole reason a third-party driver cannot pin
the framework. A driver's floor is `omniweave-ports >=1,<2`; a core upgrade is therefore never blocked
by a driver's resolver constraint. Two counter-examples set the price of getting this wrong. docling
makes `torch` and `torchvision` base dependencies of the parsing library
(`docling/pyproject.toml`, 33 required dependencies), so every consumer of a DOCX reader pays for a
tensor runtime because the packaging boundary was drawn around the project rather than around the
contract — a **≈2.5–3.5 GB** install with default CUDA wheels, **≈700 MB–1 GB** if `torch+cpu` is
pre-installed, plus weights fetched at first use. graphrag draws it correctly and shows the payoff in
the same repository: `packages/graphrag-chunking/pyproject.toml` declares
`["graphrag-common==3.1.2", "pydantic~=2.13"]`, so `pip install graphrag-chunking` is two transitive
packages, while the umbrella `graphrag` package pulls `spacy` + `blis` + `nltk` + `textblob` + three
unconditional Azure SDKs for a realistic installed size of ≈1–1.5 GB plus downloaded model data. The
split is the difference between those two numbers, in one repository, under one licence.

**Three rows to read twice.** `omniweave-vision` is the only `UNBOUNDED` ceiling and the only
distribution exempt from the 250 MB aggregate gate; it must print its resolved installed size during
`ow doctor`, because a plan that promises a number for a CUDA wheel set is lying.
`omniweave-target-docx` is deliberately **not** in `[recommended]`: a second real target exists to
falsify "one implementation wearing an interface", not to be installed by default. And
`omniweave-core` ships one piece of generated package data no other distribution ships — the
first-party release manifest of §7.2 — which is why it is the only distribution built twice in the
`build` job.

**The attachment distributions, separately versioned and outside the fourteen.** Five wheels exist to
attach omniweave to somebody else's type system. None is `RELEASE`-versioned, none appears in
`first_party.toml`, and none is in the 250 MB aggregate gate, because each tracks a third party's
minor series rather than omniweave's — which is the same reason `omniweave-ports` is versioned by
Port major (§6.2). **None of the five declares `compile`**, so none is the `compile` branch of the
layer rule — that branch is a *driver* rule (§3.4) and its worked shape is `omniweave-target-pptx`,
one of the fourteen, not an attachment. Each of these five declares
`["omniweave_core","omniweave_ports"]` in `tools/layers.toml`, because each imports `omniweave_core`
for `serialize()` and the `Scope` types — the `deps` column below says so on every row. An
attachment is imported by name from the other side rather than discovered through an entry point,
so §1.10's derived-never-chosen rule reaches it only for whatever driver entry points it also
ships. The distribution that holds **both halves of a two-way adapter** is `omniweave-docling`: one
`parse/1` driver in and `serialize()` out, in one wheel, which is the shape this table exists to
permit. *(Build note, D909: `omniweave-langchain` is built, and two of this paragraph's facts moved by user rulings of 2026-10-21.
```toml
# packages/omniweave-core/pyproject.toml — the build half, identical in shape in all fourteen
[build-system]
requires = ["hatchling>=1.27"]
build-backend = "hatchling.build"

[tool.hatch.build.targets.wheel]
packages = ["src/omniweave_core"]

[tool.hatch.build.targets.sdist]
```

`hatchling>=1.27` is a floor with a reason, which G7 requires: PEP 639's
`license = "Apache-2.0"` SPDX string plus a `license-files` glob needs core metadata 2.4, and
hatchling emits 2.4 only from 1.27. Below it the same two keys silently produce a wheel whose
`METADATA` carries a free-text `License:` field and no `License-File` entries, so every attribution
file §9.1 requires would build clean and ship absent.

The nine `LAZY` names are a **structural** property, not a convention: `__init__.py` exposes them
through `__getattr__` and G17 asserts that a bare `import omniweave_core` loads none of
`{model, store, archive, retrieve, answer, out, host, toolchain, modelserver}`. G23 additionally
asserts neither `asyncio` nor `selectors` appears. The reason is the per-turn hook path — `ow hook
prompt` has a p95 budget of 250 ms warm (G26) and pays for every module that `import omniweave_core`
touches. graphify measured the other end of that curve from inside a git hook: *"a probe that imports
graphify wholesale executes the full package import (10s+ cold on machines with AV-scanned or large
site-packages) and used to run up to FOUR times synchronously, stalling every commit before the
detached launch even started"* (`graphify/hooks.py`, `_GFY_PROBE`). Their fix is the one this layout
makes unnecessary: probe with `importlib.util.find_spec` and never `import`.

### 1.5 Inside a driver distribution — the shape every third party copies

```text
packages/omniweave-pdf/
├── pyproject.toml
│     dependencies = ["omniweave-ports >=1,<2", "pypdfium2>=4.30,!=4.30.1", "defusedxml>=0.7.1"]
│     [project.entry-points."omniweave.drivers"]
│     "parse.pdf.pdfium" = "omniweave_pdf"        # A DOTTED PACKAGE. No ':', no path.
│     [dependency-groups] dev = ["omniweave-conform"]   # the testkit is DEV-ONLY
├── LICENSE  NOTICE  THIRD_PARTY.md  LICENSES/   GENERATED; THIRD_PARTY.md lists pdfium
├── src/omniweave_pdf/
│   ├── driver.toml              THE CARD. Read by tomllib, never imported (INV-4).
│   ├── __init__.py              exports the class the card's `entrypoint` names (module:attr)
│   └── …
└── tests/                       the conformance run + the driver's own tests
```

Two grammars that look alike and are not: the **entry-point value** is a colon-free dotted package
path, and the **card's own `entrypoint` key** is `module:attr` — the one place a colon is legal —
because `activate()` must assert the loaded class's `PORT` and `SCHEMA_VERSION` against the card
before any work. [The driver system](04-driver-system.md) §4.1 owns both grammars.

The charter's justification for the colon-free form is that `setuptools._entry_points.validate`
raises at build time on a path-shaped value. **That justification does not protect this repository**,
and saying so matters: all fourteen distributions build with `hatchling`, which writes
`entry_points.txt` from the table without validating the value's shape at all. So a malformed
first-party entry-point value would ship, and the failure would surface on a user's machine as a
discovery-time refusal. G4 therefore asserts the shape directly while it is already reading every
`[project.entry-points."omniweave.drivers"]` table to derive `layers.toml` rows: each value matches
`^[a-z_][a-z0-9_]*(\.[a-z_][a-z0-9_]*)*$`, contains no `:` and no `/`, and names a package that
exists in that distribution's `src/`. A third party using setuptools gets the same rejection one
layer earlier, from their own build backend; a third party using hatchling gets it from
`ow conform`'s `card` suite.

Note what the first-party driver distributions demonstrate by being packaged exactly this way: none
of `omniweave-office`, `-pdf`, `-vision`, `-graph`, `-llm` declares a version-bearing dependency on
anything first-party except `omniweave-ports >=1,<2`. That is why a `RELEASE` bump rewrites no
constraint in five of the fourteen `pyproject.toml` files (§4.2), and it is the same property a third
party gets for free. The `!=4.30.1` above is docling's habit adopted deliberately
(`docling/pyproject.toml`: `pypdfium2 (>=4.30.0,!=4.30.1,<6.0.0)`): a specific known-bad release
excluded by exact version is more honest than a raised floor, because a floor also forbids the
releases below the bad one that were fine.

### 1.6 `toolchains/` — the whole of the second language

### 1.9 `.gitattributes`, and why a byte-diff gate needs one

```text
# .gitattributes — the eol contract. Without it, G6 and G25 fail on the Windows cells.
*                       text=auto eol=lf
schema/**               text eol=lf
schema/expected/**      -diff
docs/reference/**       text eol=lf
*.owdoc                 binary
*.sql                   text eol=lf
omniweave.index.lock    merge=ow-index-lock
```

Six of the nineteen PR jobs run on Windows or macOS — six of the nine `test` cells — and five gates
are byte-diff gates over generated text: G6 (`schema/`), G18 (`config_axes.toml`), G20
(`events.toml`), G25 (the seven agent-facing artefacts) and `gates.reference_docs`
(`docs/reference/**`). Git's `core.autocrlf` on a Windows developer's machine rewrites committed text
at checkout, so a generator that emits `\n` and a working tree that holds `\r\n` disagree
byte-for-byte for reasons that have nothing to do with the code. Three rules close it, and all three
are needed:

1. **`.gitattributes` pins `eol=lf`** for every generated tree, so the checkout matches the
   generator on all three OSes.
2. **Every generator writes `"\n"` explicitly** — `open(path, "w", newline="\n")`, never the
   platform default. semgrep bans a bare `open(..., "w")` under `tools/` and `omniweave/gen/`.
3. **Every `--check` normalises CRLF before comparing**, which is the charter's own wording for G6
   ("byte-diff, CRLF-normalised") applied to all five. hyperframes' bundle hasher is the mechanism
   worth copying wholesale (`packages/cli/src/utils/skillsManifest.ts:179-197`): sort by full path so
   the digest is filesystem-order independent, fold the relative path into the hash so a moved file
   changes it, and normalise `\r\n` → `\n` for a declared text-extension set. The same three
   decisions apply to every `--check` gate here.

**The last line is a promise git does not keep by itself, and that is a shipped failure mode.**
`merge=ow-index-lock` names a merge driver; it does not install one. A driver lives in the developer's
`.git/config`, which is not tracked, so a fresh clone silently falls back to the default text merge —
and the default text merge unions both sides' lines, which is exactly the property
`omniweave.index.lock`'s driver exists to refuse (a deleted line must stay deleted; graphify's
`nx.compose` union driver is the recorded counter-example, `graphify/cli.py:2572`, with caps
`_MERGE_MAX_BYTES = 50 MB` and `_MERGE_MAX_NODES = 100_000` two to three orders below a real corpus).
Three mechanisms, because one is not enough: `ow store git-install` writes the
`merge.ow-index-lock.driver` entry; `ow doctor` reports `index-lock merge driver: not installed` with
that command as the fix; and the driver itself writes a conflict marker naming `ow store merge-lock`
rather than resolving, so an *absent* driver produces a wrong file and a *present* driver produces a
stopped merge. Only the second outcome is recoverable, which is why `ow doctor` checks for it rather
than assuming it.

### 1.10 Adding a distribution, and why removing one is not symmetric

The number fourteen is a literal in this document, in charter §3.2 and in `docs/ARCHITECTURE.md`.
`tools/gate_docs.py` clause d2 resolves it against `len(glob("packages/*/pyproject.toml"))`, so the
literal cannot drift silently — but nine other places move with it, and a PR that misses one produces
a distribution that builds, publishes and then behaves wrongly. The fan-out, in the order a reviewer
should check it:

| # | site | what changes | what fails if you forget |
|---|---|---|---|
| 1 | `packages/<dist>/pyproject.toml` | the new file, with `hatchling>=1.27` and the two hatch target tables | — |
| 2 | `packages/<dist>/{LICENSE,NOTICE,THIRD_PARTY.md,LICENSES/}` | four generated attribution files | `gen_notice.py --check` inside G3 |
| 3 | `tools/layers.toml` | one row, **derived** from the entry points, never chosen | G4 |
| 4 | `tools/weights.toml` | one `[dist."…"]` table with `marginal_mb` and a `why` line | G2 (an unlisted distribution has no ceiling and fails closed) |
| 5 | `packages/omniweave/pyproject.toml` extras | one alias row, unless the dist is `core`, `ports` or `conform` | G14's totality clause |
| 6 | `tools/check_versions.py` | the expected site count moves from 40 | G5 |
| 7 | §1.2 here, and `docs/ARCHITECTURE.md`'s module table | one row each | G27 d1, d2 |
| 8 | `.github/CODEOWNERS` | a path rule, if it is contract-bearing | — (a review-routing miss, not a build failure) |
| 9 | the `build` job's wheelhouse assertions | the `--all-packages` install count | `build.wheelhouse_profiles` |
| 10 | §8.3's commit-scope allowlist | one scope | the commit-message gate |

An **attachment distribution** (§1.2's second table) is a different animal: it takes sites 1, 2, 3, 4
and 8, skips 5, 6, 7, 9 and 10 because it is not `RELEASE`-versioned, is not in `first_party.toml`, is
not in an extra and is not in the `--all-packages` wheelhouse assertion, and it names its own
third-party floor rather than inheriting one.

The first-party release manifest is deliberately **not** on that list: `gen_first_party.py` reads
`dist/` and needs no declaration, which is the property that makes step 13 of §7.6 a count check
rather than a diff review.

**Removing a distribution is not the inverse of adding one, and the asymmetry is a PyPI fact.** A
published distribution name is permanently consumed: the last release of it stays installable
forever, and the moment it leaves `first_party.toml` every installed copy flips from `first_party` to
`unpinned` ([the driver system](04-driver-system.md) §4.2) — which, under the shipped
`require_lock = true`, turns into `NOT_IN_LOCKFILE` and a refusal on a machine nobody touched. So the
retirement path is three releases and no shorter:

1. **Release N.** The distribution becomes an empty shim whose only dependency is its successor, and
   whose entry points are removed. Its `layers.toml` row becomes `[]`, its `weights.toml` ceiling
   drops to 1 MB, and its drivers ship as framework tombstones under the old `DriverId`s so a
   resolution names the successor rather than failing blank.
2. **Release N+1.** It is still built, still in `first_party.toml`, still published. Nothing changes
   for a consumer who has not upgraded.
3. **Release N+2.** It stops being published and leaves `first_party.toml`. `omniweave`'s extra for
   it is removed in the same release, which is a CLI-surface removal and therefore a `RELEASE` MAJOR
   under §4.3 unless the extra was never published.

The `omniweave-*` prefix is never reused for a different thing, for the same reason a `codes.toml`
row is never renumbered.

## 2. Package boundaries, extras and install profiles

### 2.1 What belongs in `omniweave-core`, stated as four tests

A PR that adds a module to `omniweave-core` must be able to answer yes to all four. Any no means the
module belongs in `omniweave` (host behaviour), in `omniweave-ports` (a type a driver needs) or in a
sibling distribution.

| # | test | why | enforcer |
|---|---|---|---|
| 1 | **Does it need zero third-party imports?** | `import omniweave_core` is on the per-turn path of every hook and CLI call; a compiled extension there is a fixed tax paid by `ow hook prompt`'s 250 ms p95 | G1 (clean-environment resolve), G9 (`-X importtime` shows zero third-party modules) |
| 2 | **Is it called by two or more surfaces, or by both a driver-facing and a host-facing caller?** | the reason `retrieve` and `answer` are in core rather than in `omniweave-serve` is that MCP, the CLI and the SDK call one implementation and none of them owns it | G4: `omniweave_serve`'s row is `["omniweave_core", "omniweave_ports"]`, so it can never import `omniweave` |
| 3 | **Can it be imported lazily, or is it small enough to be eager?** | the nine lazy subpackages exist because `model`, `store`, `retrieve` and `out` are each larger than the whole eager surface | G17, G23 |
| 4 | **Is it synchronous?** | the single event loop lives in `omniweave/run/supervisor.py` ([the runtime](08-runtime.md)), in the CLI distribution, precisely so core pays no loop-import tax | G23 asserts core imports neither `asyncio` nor `selectors` |

The four things the design rulings asked core to import and what replaced each — a MessagePack codec,
a JSON Schema validator, `pydantic`, `zstandard` — are recorded in charter §D1 with their costs. The
pattern is worth internalising: each replacement is 80–250 lines of first-party code with a property
test, and each purchase would have been a permanent dependency on the framework's hottest import path.
`omniweave-core` declares exactly one optional dependency, and it is a **capability remedy** rather
than a feature: `[sqlite] = ["pysqlite3-binary>=0.5"]`, named by `store/sqlite.py`'s refusal when the
interpreter's SQLite lacks FTS5 or is below `MIN_SQLITE = (3, 42, 0)`. No other core extra may exist,
because an extra that adds a capability makes INV-2 conditional.

### 2.2 What is an extra, and the 1:1 alias rule

`omniweave`'s extras are a **1:1 alias map onto `omniweave-*` siblings**, so `pip install
omniweave[vision]` and `pip install omniweave-vision` resolve identically. There is no `[all]`, no
`[everything]`, and no extra may name a third-party package (G14).

```toml
# packages/omniweave/pyproject.toml — the extras block, complete, at RELEASE 0.4.2.
# GENERATED by tools/check_versions.py --set; asserted by G5. Do not hand-edit a bound.
[project.optional-dependencies]
office = ["omniweave-office ~= 0.4.0"]
pdf = ["omniweave-pdf ~= 0.4.0"]
vision = ["omniweave-vision ~= 0.4.0"]
graph = ["omniweave-graph ~= 0.4.0"]
llm = ["omniweave-llm ~= 0.4.0"]
serve = ["omniweave-serve ~= 0.4.0"]
pptx = ["omniweave-target-pptx ~= 0.4.0"]
docx = ["omniweave-target-docx ~= 0.4.0"]
deck = ["omniweave-target-deck ~= 0.4.0"]
video = ["omniweave-target-video ~= 0.4.0"]
recommended = ["omniweave-serve ~= 0.4.0", "omniweave-pdf ~= 0.4.0", "omniweave-target-pptx ~= 0.4.0"]
```

**The bounds are literal text in the file, written by a tool.** There is no packaging mechanism by
which a `uv` workspace synthesises a version bound into a built wheel's metadata — `[tool.uv.sources]`
governs *where* a workspace member resolves from during development and is absent from the published
`METADATA` entirely. So the thirteen sibling constraints and the extras block above are written into
the file by `tools/check_versions.py --set <RELEASE>` and read back by G5. `~= 0.4.0` expands to
`>= 0.4.0, == 0.4.*`, which is why a PATCH release rewrites only the `version` fields and a MINOR
release rewrites the bounds as well — a distinction §4.2 counts exactly.

`omniweave-conform` is deliberately **absent** from the map: an extra on the runtime distribution that
pulls `pytest` is exactly how test-only weight lands in a production install. `markitdown-ocr` is MIT
on the tin and hard-requires AGPL PyMuPDF through the same door
(`markitdown/packages/markitdown-ocr/pyproject.toml:31`). A driver author dev-depends on
`omniweave-conform` directly, in a `[dependency-groups] dev` list, which no consumer resolves.

> **Extends the charter.** The extra name is the sibling name with `omniweave-` and any leading
> `target-` stripped. The charter fixes the rule (1:1, siblings only) and shows `[vision]`; it does
> not fix the spelling of the other ten. The spelling is markitdown's, which is the one packaging
> decision in that repository worth copying wholesale — one extra per format, named after the format
> (`pptx`, `docx`, `xlsx`, `pdf`, `outlook`, `markitdown/packages/markitdown/pyproject.toml:31-58`) —
> so `pip install "omniweave[docx,pdf]"` reads the way a user guesses it. A gate asserts the map is
> total (every sibling except `omniweave-conform`, `omniweave-core` and `omniweave-ports` has an
> extra) and injective (no two extras name the same sibling), so a new distribution cannot ship
> without an install path and cannot ship with two.

**Why distributions and not extras, in one number.** DataFlow ships 20 extras of which four pin
mutually incompatible vLLM ranges (`vllm>=0.7.0,<=0.9.2`, `vllm<0.8`, `vllm<0.9`, `vllm==0.6.3`), so
`[kbc]` + `[mineru]` is unsatisfiable — under a `requires-python = ">=3.7, <4"` that is false by three
minor versions, since the code uses `list[str]`, `int|None`, `ParamSpec` and `TypeAlias`, and nothing
tests it. Extras cannot express "these two cannot coexist"; separate distributions can, because each
is an independent resolver root. markitdown's extras additionally show the hazard an alias map
removes: `audio-transcription = ["pydub", "SpeechRecognition"]` sends audio to Google's free Web
Speech endpoint by default, and nothing in the extra's name or the README's security section says so.
An extra that may name only a first-party sibling cannot introduce an egress path, because the
sibling's own card and G15 own that question.

### 2.3 The install profiles

An **install profile** is a named, tested install command — not a documentation heading. (The lock
reserves bare *Profile* for the agent surface's listed-set, so this document says "install profile"
wherever the two could be read together.) `ceiling sum` is the sum of the `tools/weights.toml` rows
the profile installs — the number G2 enforces, and an upper bound rather than a measurement. The
measured value per OS and Python is recorded in `eval/baselines/weights-<os>-<py>.json`, produced by
the `build` job's wheelhouse install (§6.6), and is what `ow doctor` prints.

| install profile | command | adds | ceiling sum | what it can do |
|---|---|---|---|---|
| **laptop, minimum** | `pip install omniweave` | ports, core, omniweave, office | **47 MB** (1+6+25+15) | DOCX/ODT/RTF/EPUB/CSV/TXT/MD/HTML at document grain; four retrieval channels; no PDF, no MCP, no OUT |
| **laptop, working** | `pip install "omniweave[recommended]"` | + serve, pdf, target-pptx | **177 MB** (47+40+30+60) | the above plus PDF, the MCP server and PPTX compilation. The G2 aggregate ceiling is 250 MB, so 73 MB of headroom is deliberate: it is what a licence-clean ANN backend (F10) and a `deck` rasterizer (F18) must fit inside |
| **CPU server** | `pip install "omniweave[recommended,graph,llm,docx]"` | + graph, llm, target-docx | **204 MB** (177+5+2+20) | the structure-extraction ladder, the four billed LLM passes (off by default), DOCX out |
| **GPU server** | `pip install "omniweave[recommended,graph,llm,vision]"` | + graph, llm, vision | **184 MB + torch** (177+5+2+0) | per-page VLM escalation, which is `parse.page.olmocr` and no `derive.*.vlm` pass ([ADR-8](adr/0008-input-surface-and-pass-ladder.md) D8.3). The `vision` row is `UNBOUNDED` because a CUDA 12 wheel set is 2.5–6 GB depending on variant; `ow doctor` prints the resolved number and the plan does not promise one |
| **browser** | — | nothing | **0 MB** | see below |
| **CI** | `uv sync --frozen --all-packages --group dev` | all 14 except vision, plus the dev group | **214 MB + dev** (the thirteen bounded rows) | the dev group's own weight is dominated by `semgrep` and `torch`-free `hypothesis`/`atheris`; it is not gated, it is not shipped, and the `parity` container installs `pytest` alone so the parity claim is not measuring the dev group |

Two of those sums deserve their arithmetic spelled out because reading the table wrong is easy. The
**CI** row is every bounded ceiling: `1+6+25+15+30+40+5+2+60+20+1+1+8 = 214`. The **GPU server** row
is *not* the CPU-server sum plus vision — it drops `docx` (20 MB) and adds `vision` (0 MB bounded),
so it is 184, and it is the one install profile whose ceiling sum is smaller than the one above it
while its real installed size is an order of magnitude larger. That asymmetry is the reason
`omniweave-vision`'s exemption is stated on the row rather than in a footnote.

**There is no browser install profile, and inventing one would be the wrong answer.** omniweave does
not run in a browser: the `wasm` `DriverHost` is declared and not built at v1, `omniweave_core.store`
holds the only `sqlite3.connect` in the framework, and the whole retrieval path is a SQLite reader.
What a browser gets is a **generated client**: `ow surface typescript <dir>` emits `omniweave.d.ts`
plus a ~120-line zero-dependency client that either spawns `ow --render json` or POSTs to
`ow serve --http`, both from the same committed, byte-diff-gated `schema/*.json` ([system
architecture](02-architecture.md) §2 rows 31 and 33). Zero bytes of omniweave ship to the browser and
the types cannot drift, because they come from the gate.

**Cold start does not vary by install profile, and that is a structural claim.**

```text
                                        budget       gate   varies with profile?
  import omniweave_core                 <=  80 ms    G10    no  — zero third-party (G9)
  ow --version                          <= 150 ms    G10    no
  ow --help                             <= 250 ms    G10    no  — the verb tree is generated data
  driver discovery, 20 installed        <=  20 ms    G10    yes, sub-linearly: entry_points()
                                                            measured 15.3 ms at 328 distributions
  ow query, warm store                  <= 250 ms    G10    no
  ow hook prompt, warm                  <= 250 ms p95 G26   no
```

The GPU profile's `ow --help` equals the laptop profile's because `torch` is imported by
`omniweave_vision`, which is imported only by `activate()`, which runs only inside a `subproc`
worker. That is not luck: INV-4 (discovery never executes driver code) plus G17 (core imports no lazy
submodule) plus rule 3 of the dependency rule (a parse driver imports `omniweave_ports` and nothing
else of ours) together make it impossible for a driver's weight to reach the CLI's import path. The
one number that does move is discovery, and it moves against the count of *installed distributions*
rather than of omniweave's — `entry_points(group=…)` measured **15.3 ms at 328 distributions** on
Windows / 3.11.9 warm, against **2124 ms** for a `Distribution.files` (`RECORD`) scan over the same
set, which is why a `RECORD` walk is forbidden as a discovery mechanism and permitted only inside
`gate_weights.py`, where it runs once in CI and never on a user's machine.

The comparison worth naming is markitdown's. Its core manifest is six dependencies —
`beautifulsoup4`, `requests`, `markdownify`, `magika~=0.6.1`, `charset-normalizer`, `defusedxml`
(`markitdown/packages/markitdown/pyproject.toml:21-28`) — which reads like ≈20 MB, while `magika`
pulls `onnxruntime` and `numpy` and the real minimal install is ≈150–250 MB. That is the failure mode
`tools/weights.toml` measures away by gating on `RECORD` in a fresh environment rather than on the
dependency list. `ow --version` prints `RELEASE`, `CONTRACT` and `SCHEMA` on one line for the same
reason: the three numbers a support request needs are the three a manifest cannot show. `SCHEMA`
prints as `<major>.<minor>`, formatted at the one site §4.1 names from `omniweave_core.contract`'s
`SCHEMA` and `SCHEMA_MINOR`.

### 2.4 Verifying an install profile is an install profile

Three of the six are built in the `build` job from the wheels that release will publish, into fresh
virtual environments, from an offline wheelhouse (§6.6), and each one carries one assertion that
fails loudly. The three together are the `[[job_assertion]]` `build.wheelhouse_profiles`.

| install profile | the assertion `build` makes |

and the reason omniweave cannot copy it is that a refusal naming a remedy is the product surface, not

### 2.5 `tools/weights.toml`

```toml
# tools/weights.toml — G2. Raising a number requires the `why` line and a reviewer.
schema = 1
aggregate_mb = 250

[dist."omniweave-ports"]
marginal_mb = 1
why = "pure typing, no third party"

[dist."omniweave-core"]
marginal_mb = 6
why = "stdlib only; the number is the source tree plus generated and packaged data (the migrations, the schema, the error-code register). Raised from 3 MB by a user ruling of 2026-10-19 (option a, reviewed): release 1's core measures 4.64 MB installed, the store, retrieval, host and OUT framework having grown past the section 1.2 estimate, and 6 MB is that with headroom, not a licence to vendor anything heavy -- core still imports no third-party module (G9)."

[dist."omniweave-pdf"]
marginal_mb = 30
why = "pypdfium2 bundles the pdfium binary; defusedxml is negligible"

[dist."omniweave-vision"]
marginal_mb = 0
unbounded = true
why = "torch + transformers; ow doctor prints the resolved size (the G2 exemption)"
```

> **Extends the charter.** The charter's distribution table gives one `ceiling` column and the
> terminology lock defines a Weight ceiling as "the per-distribution installed-size limit … measured
> from `RECORD` in a fresh environment". Read as a *closure*, the column is internally inconsistent:
> `omniweave-target-deck`'s ceiling is 1 MB while its dependency `omniweave-core`'s is 3 MB, and a
> closure cannot be smaller than something it contains. The column therefore reads **marginal**,
> decided by [ADR-10](adr/0010-data-artefacts-and-weight-ceiling.md) and carried into the charter by
> erratum `E79`, which makes this section the reading's sole home rather than a correction filed
> against one. A row is the distribution's own installed files plus the
> third-party closure it introduces, excluding first-party siblings, each of which is counted in its
> own row. `aggregate_mb` is then the only *union* number, measured by actually installing
> `omniweave[recommended]` into a fresh environment and summing every `RECORD`. Both numbers are
> produced by `tools/gate_weights.py`, which prints **both numbers on every run, pass or fail** —
> the per-row sum and the deduplicated union — so the gap between them is never inferred, and on a
> failure adds a per-row table naming the row, its ceiling, its measured value and the largest three
> files that moved. The lock's Weight-ceiling definition gains the word in ADR-1's bulk pass.

Four failure modes the gate must handle rather than assume away. *(Build note, D899: G2's measured half now runs in the `build` job, in `tools/check_wheelhouse.py`'s all-but-vision profile, over the thirteen bounded distributions installed offline. Its first run found two rows over, and both ceilings were raised by user rulings with a `why` line: `omniweave-core` 3 -> 6 MB (4.64 MB measured; ruling of 2026-10-19) and `omniweave-conform` 5 -> 8 MB (7.48 MB, pytest 9's Pygments; ruling of 2026-10-20). Every other row is under; the union is 97.9 MB of 250.)*

1. **Runtime-downloaded data contributes nothing to `RECORD`.** A wheel that fetches a model or runs
   a `postinstall` is unbounded weight the measurement cannot see, which is exactly why
   `omniweave-vision` is unbounded and why `revision="main"` is a lint error (G8): an unpinned
   weights revision is unbounded weight with no declaration site. `ffmpeg-static`'s postinstall
   download is the mined shape of the same hazard on the npm side
   (`hyperframes/packages/aws-lambda/package.json`), and it is why §9.3 lists it.
2. **A shared third-party dependency counted in two rows double-counts against `aggregate_mb`.**
   `gate_weights.py` computes the union by deduplicating on installed path, not by summing rows, and
   reports the per-row sum alongside it on **every** run, pass or fail, so the gap is visible before
   a gate fails rather than only after.
3. **`RECORD` is a manifest, not a filesystem.** A wheel may install a file it does not list, and a
   `.pth`-installed package lists almost nothing. The gate therefore measures **both** — the `RECORD`
   sum and `du` over `site-packages` after the install — and fails on a discrepancy above 5%, naming
   the unlisted paths. Without the second measurement the gate can be defeated by any dependency that
   writes outside its own `RECORD`.
4. **Compiled artefacts appear after first import.** `__pycache__` is written on first run, not on
   install, so the measurement is taken after `python -c "import omniweave"` rather than immediately
   after `pip install`, and the difference is reported as its own line. Measuring before first import
   understates a pure-Python distribution by roughly the size of its source.

### 2.6 Package data is read at use time, never at import time

Five kinds of file ship inside a wheel and are read at run time: `omniweave_core/drivers/
first_party.toml` (§7.2), `omniweave_core/store/schema/migrations/*.sql` (§5.1),
`omniweave_core/drivers/tombstones/*.toml`, each driver distribution's `driver.toml`, and
`omniweave/skills/**`. Three rules bind all five, and each is a recorded defect elsewhere.

1. **Read through `importlib.resources.files(<package>)`, never `__file__` and never
   `__path__[0]`.** A zipapp, a `pip install --target` layout and any `zipimport`er give a package
   with no usable filesystem path, and `__path__[0]` then either raises or names a directory that
   does not contain the file. semgrep bans `__file__` and `__path__` under `packages/*/src/`.
2. **Read at use time, memoised, never at import time.** graphify's `install.py:35-57` states the
   reason in its own docstring — *"Deferred to use-time so a missing/corrupt packaged block can't
   crash module import (which would brick every CLI command, not just install)."* A missing
   `first_party.toml` must degrade one trust computation, not make `ow --version` fail.
3. **A missing or unparseable file raises a named `OwError` carrying the command that clears it**,
   never a `KeyError`, a `FileNotFoundError` or a silent empty default. graphify raises
   `RuntimeError("graphify install is incomplete: missing always-on block …  Reinstall …")`; the
   omniweave form is an `OwError` with a `codes.toml` row and a `.fix` string, because §6.4 of the
   charter requires every message to end with the command that clears it. *(Build note, D897: a sixth packaged file, `omniweave_core/codes.toml`. An installed release had no register, so every error printed its symbol alone and `ow explain` resolved nothing, while section 2.4's minimum profile asks for the `OW-D-*` code as declared. It is a committed copy of the root register (section 1.1's home, G13's input), held byte-identical by `test_codes_packaged.py`; a `force-include` of the root file is D12's defect.)*

The consequence worth stating out loud is `first_party.toml`'s. It is generated **into** `src/` by
the `build` job, is `.gitignore`d, and therefore does not exist in a developer's checkout at all. A
workspace install (`uv sync`, `pip install -e`) consequently has no manifest, `compute_trust` returns
`unpinned` with a `Degradation(kind="pin")`, and that is correct rather than a gap: an editable
checkout has no wheel and therefore no `dist_sha256` to attest. It is also why §2.4's wheelhouse
installs matter beyond weight measurement — the `conform` job runs against installed wheels precisely
so trust computation is exercised on the shipped shape, and a developer's checkout never silently
gets a trust level a user would not.

## 3. The multi-language story

### 3.1 Two languages, and where the line is

There are exactly two languages and one boundary. Python owns the document model, the store, every
index, the router, the runtime and eleven of the twelve first-party drivers. TypeScript exists only
as **Toolchains** — digest-pinned non-Python execution bundles invoked as a one-shot child over
`omniweave-target/1` — and only for the two OUT targets that need a browser-grade layout engine
(`deck`, `video`).

The boundary is drawn where it is because of one fact: **L2 never crosses a language boundary.** A
Toolchain receives an IL bundle (canonical SVG or HTML, text on disk) and an asset directory; it never
receives a `Block`, a `Doc`, a `Snapshot` or a `block_id`. Consequently there is no cross-language
document model, no IDL and no shared schema compiler — the language-neutral contract is *generated*
JSON Schema emitted from the Python definitions, committed to `schema/`, and byte-diff gated (G6).
Rejected explicitly: protobuf, Cap'n Proto, Arrow and schemars-from-Rust, each a fourth toolchain and
a second source of truth for a boundary carrying a ~30-field job envelope and a receipt. proto3's
all-optional field model additionally cannot express "every block carries an origin and a confidence".

There is no first-party Rust. The one compiled dependency in the framework is someone else's
published MIT `abi3` wheel (`firecrawl-anydoc == 0.2.4`), consumed in-process behind
`omniweave-office`, with its source vendored at a recorded SHA under `vendor/anydoc/` and a written
`FORK-TRIGGER.md`. We do not build it, and no `packages/*/pyproject.toml` declares a
`[build-system]` other than `hatchling`.

### 3.2 How artefacts cross the boundary

```text
  PYTHON                                                          TYPESCRIPT
  omniweave_core.toolchain.run(spec, job_dir, timeout_s, ctx)
        |
        |  1. resolve node:  $OMNIWEAVE_NODE
        |                 -> $OMNIWEAVE_HOME/node/<version>-<platform>/bin/node[.exe]
        |                 -> `node` on PATH IF it satisfies spec.node_range
        |                 -> none: the target is PRUNED FROM THE PLAN with a report naming
        |                    `ow targets install <name>`. Never an ImportError.
        |  2. verify the FULL sha256 of the app bundle. A mismatch is
        |     FAILED_PERMANENT(TOOLCHAIN_DIGEST) and NEVER triggers a fetch.
        |  3. spawn with cwd = job_dir ALWAYS and env = a constructed allowlist
        v
  +- stdio: omniweave-target/1, NDJSON, stdout CONTROL ONLY, < 1 MiB per invocation ---+
  |   hello -> ready -> {validate|compile|project} -> progress* -> result -> bye       |
  |   stderr is a log, drained on a dedicated thread, kept as a bounded ring, NEVER    |
  |   parsed.  exit 0 IFF a receipt was written.                                       |
  +------------------------------------------------------------------------------------+
        |
  +- job directory: the DATA plane. Blobs never travel on stdio. ----------------------+
  |  <cache_root>/jobs/<run_id>/<artifact_slug>@<gen>/                                 |
  |  |-- job.json        Python -> TS   validated against schema/job-v1.json           |
  |  |-- brief.md        Python -> TS   the frozen brief                               |
  |  |-- il/             Python -> TS   canonical SVG / HTML, TEXT ON DISK             |
  |  |-- assets/         Python -> TS   index.json + cas/ab/cd/<sha256>, FROZEN        |
  |  |-- validation/     TS -> Python   early.json / final.json (FindingSets)          |
  |  +-- out/            TS -> Python   the artefact + receipt.json + <slug>.owcite.json|
  +------------------------------------------------------------------------------------+
```

Five properties of that boundary are worth stating because each is a recorded bug elsewhere:

- **`cwd` is always the job directory, never inherited.** graphify has four recorded CWD bugs; semgrep
  bans `os.getcwd()` and `Path(".")` in library code for the same reason (G8).
- **The digest is in the path and verified on every invocation.** `$OMNIWEAVE_HOME/toolchains/` is a
  user-writable directory holding executable code; the digest is the only thing between a compromised
  home directory and arbitrary execution, and `--offline` refuses to fetch. The charter says plainly
  that a compromised home directory is compromised and no substrate choice fixes it.
- **The digest is the *full* sha256, not a 16-hex prefix.** 64 bits is weak against intent.
- **A missing runtime prunes the target and reports the install command.** It is never an
  `ImportError`, and never a silent substitution of a different renderer or codec: libvpx/AV1 absent
  means the mp4 target refuses.
- **Windows invokes `node.exe` against the entry directly, never a `.cmd`/`.bat` shim.** Modern Node
  throws `EINVAL` on a direct `spawn` of a `.cmd` since the CVE-2024-27980 hardening — codegraph's
  recorded scar, verified live on their Windows VM (`codegraph/src/upgrade/index.ts:634-637`,
  `codegraph/BUNDLING.md:55`) and regression-tested in two of their suites. Their workaround is to
  route through `cmd.exe`; omniweave's is to never resolve a shim in the first place, which is why the
  node ladder above names `bin/node[.exe]` rather than a directory to search.

**The app bundle and the runtime are two artefacts with two owners, and `tools/toolchains.toml` has
two tables because of it.**

```toml
# tools/toolchains.toml — read by omniweave_core.toolchain. It NEVER reads the network.
schema = 1

[[toolchain]]
name = "deck"
version = "0.4.2"
entry = "dist/render.mjs"
node_range = ">=20.11,<23"
bundle_sha256 = "sha256:1f0c9a…"
bundle_url = "https://github.com/omniweave/omniweave/releases/download/v0.4.2/omniweave-toolchain-deck-0.4.2.tar.gz"

[[node]]
version = "20.18.1"
platform = "linux-x64"
sha256 = "sha256:4b8e11…"
url = "https://nodejs.org/dist/v20.18.1/node-v20.18.1-linux-x64.tar.xz"
```

The split is the whole reason there is no platform matrix here. The **app bundle is
platform-independent** — one `dist/render.mjs`, one sha256, one row — because esbuild emits one file
and the bundle carries no binary. The **runtime is not ours**: omniweave never repackages Node, so
each `[[node]]` row records the version, the platform tag and the sha256 **copied from nodejs.org's
own `SHASUMS256.txt` at pin time**, and `ow targets install` verifies the download against that row.
Vendoring Node as platform-tagged wheels was rejected on ordering grounds by the charter, which
priced it at "multiplies the release matrix by six"; recording six upstream digests costs six lines
and multiplies nothing, because we build none of them.

Two consequences a reviewer should check. A `[[node]]` row's `sha256` is transcribed, not computed by
us, so `ow doctor --runtime` re-verifies an installed node against its row and reports a mismatch as
`TOOLCHAIN_DIGEST` on the runtime rather than on the bundle — two digests, two messages. And the
bundle is `.tar.gz`, not `.tar.zst`: `tarfile` and `gzip` are standard library on every supported
Python, `compression.zstd` is 3.14+, and `ow targets install` lives in the `omniweave` distribution
whose closure contains no zstd decoder. That is the charter's own argument for striking zstd from
`.owdoc`, applied to the one artefact format the charter left unspecified.

**The two data artefacts are a plain ZIP and this bundle is not, and the criterion is which reader
opens them.** [ADR-10](adr/0010-data-artefacts-and-weight-ceiling.md) moves `omniweave-golden` and
`omniweave-index` off `.tar.zst` to `<name>-<version>.zip` with `ZIP_DEFLATED` members, plus the same
`manifest.toml` and `.sha256`, installed by digest into `$OMNIWEAVE_HOME/golden/<version>-<sha256>/`
(charter erratum `E78`, sole home this section). They are fetched over the network and read through
[security](14-security.md) §2.2's bounded reader, whose pre-filter is a member's declared
uncompressed size from the central directory and whose read is `cap+1` bytes **by name** — neither of
which a tar has. The Toolchain bundle is one esbuild output, verified whole by sha256 and read once
by `ow targets install`, never by that reader, so it keeps `tar` and the framework writes one bounded
reader rather than two.

`il_digest` is the one fact implemented twice in two languages. The spec is `schema/il-digest-v1.md`
(basename-sorted, `name\0sha\n` framing, and an unreadable file contributing the literal `unreadable`
plus an error row rather than silently dropping out), and a shared fixture set under
`fixtures/il-digest/` is run by both `pytest` and `vitest` in the `toolchains` job. That fixture set
is the *only* thing keeping the two implementations equal, and it is why `il-digest.ts` lives in
`_shared/` rather than once per Toolchain. Its determinism decisions are the same three §1.9 requires
of every `--check` gate, for the same reason: hyperframes' `hashSkillBundle` sorts by full path so
the digest is filesystem-order independent, folds the relative path in so a moved file changes the
hash, and normalises `\r\n` → `\n` for text extensions so a Windows checkout does not read as
different content. A cross-language digest that skips any of the three produces a parity failure on
exactly one of the nine cells, which is the hardest kind to diagnose.

### 3.3 The build toolchain per language

| | Python | TypeScript |
|---|---|---|
| package manager | `uv`, one workspace, `uv.lock` committed | `pnpm`, one workspace, `pnpm-lock.yaml` committed |
| build backend | `hatchling>=1.27`, one per distribution | `esbuild` via a root `bundle` script |
| output | 14 sdists + 14 `py3-none-any` wheels, one runner | one `dist/render.mjs` per Toolchain, ES2022 |
| lock discipline | `uv sync --frozen` in every CI cell; a stale lock fails the cell | `pnpm install --frozen-lockfile` |
| reproducibility | `SOURCE_DATE_EPOCH` = the build commit's committer date; the `build` job builds twice and diffs all 28 sha256s (`build.reproducible`, §6.6) | the `toolchains` job builds twice and diffs each bundle's sha256 (`toolchains.reproducible`); no `--define` may inject a build time, and the only value baked in is `RELEASE` |
| formatter | `ruff format` | `biome format` |
| linter | `ruff check` + `pyright` (strict) + `semgrep` | `biome lint` + `tsc --noEmit` |
| test runner | `pytest ~=9.1` with `pytest-xdist` | `vitest`, for the shared parity fixtures only |
| distribution | PyPI | **not published** — see §3.5 |
| how the digest is fixed | PyPI content-addresses the wheel; `omniweave.lock` records `dist_sha256` | `tools/toolchains.toml` records the full sha256 in-tree |

Reproducibility is a job assertion on both sides rather than a claim, because the failure is silent:
an `esbuild` output that varies run to run makes `tools/toolchains.toml`'s digest name one particular
build rather than a source state, and the first symptom is `TOOLCHAIN_DIGEST` on a machine that
downloaded the release asset from a different job than the one that wrote the row.

The TypeScript build produces a **single bundled `.mjs` with zero runtime dependencies**. That is
deliberate and it is the difference between a Toolchain and a Node project: there is no
`node_modules` in the shipped bundle, so the installed artefact is one file plus a `package.json`
stub, its sha256 is stable across installs, and a `pnpm audit` finding is a build-time concern rather
than a deployed surface. open-slide is the counter-example worth naming: `@open-slide/core` ships
`src/app` as source and resolves Vite plugins at run time, which is right for a dev server and wrong
for a digest-pinned one-shot child.

### 3.4 How a user avoids the language they do not want

**A Python user never installs Node.** No `pip install` in this framework pulls a JavaScript runtime,
because `toolchains/` is not in `packages/` and no `pyproject.toml` references it. The flagship OUT
target — PPTX — is pure Python. If a user asks for a `deck` or `video` artefact with no Node runtime,
the target is pruned from the plan, the report names `ow targets install deck`, and the plan continues
with the targets that resolved. `ow doctor` lists Toolchain presence, the resolved node path and the
node version per target, so the answer is available before a compile is attempted rather than after.

The claim is proved, not asserted, by the `parity` job: a container with no Node binary on `PATH`,
no GPU and no network, running the full suite. It is also the reason `pyright` cannot run there
(§8.2) — a type checker that silently downloads a JavaScript runtime is the one tool that would make
the Node-free claim untestable in the job whose whole purpose is to test it.

**A TypeScript user does not get a Python-free omniweave, and the docs say so.** There is no pure-TS
port and there will not be a hand-written one. The supported path is `ow surface typescript <dir>` —
generated types plus a generated zero-dependency client over either the CLI's `--render json` or
`ow serve --http` — with omniweave itself installed once, by whoever runs the corpus. Pretending
otherwise would mean a second implementation of retrieval, the Verdict and the Answer renderer, which
is the one thing this design refuses everywhere else.

**A driver author avoids everything.** A driver's whole omniweave surface is `omniweave-ports`
(~40 KB, stdlib only) plus, dev-only, `omniweave-conform`. Adding `omniweave_core` to a
non-`compile` driver's `layers.toml` row is a G4 failure with a message that names the fix.

### 3.5 What is deliberately not published

| ecosystem | at release 1 | why not, and the trigger that changes it |
|---|---|---|
| **npm** | no | there is no in-tree TypeScript consumer outside `toolchains/`, and `ow surface typescript` generates the client from the gated schemas. The written trigger in `docs/TS-SDK-TRIGGER.md`: **a first non-toolchain in-tree TS consumer, or three external requests.** Until then it is a generator, not a release rota |
| **crates.io** | no | there is no first-party Rust. The premise that justified a Rust kernel — three languages must agree on L2 byte-for-byte — is false here: L2 never reaches TypeScript and the only cross-language digest is plain sha256 over bytes |
| **platform-tagged wheels** | no | all fourteen are `py3-none-any` and build on one runner. Vendoring Node as platform wheels was rejected on ordering, not principle: it multiplies the release matrix by six before a deck target exists. §3.2's `[[node]]` table is the alternative that costs six transcribed digests and no build matrix |
| **a single-file installer** (PyInstaller, a shiv zipapp) | no | it reintroduces the per-platform matrix that `py3-none-any` exists to avoid, and it defeats INV-3's cold-start argument by folding every lazy subpackage into one startup. It also breaks §2.6 rule 1 in the one place the rule bites hardest — a frozen bundle has no `importlib.resources` filesystem for `schema/migrations/*.sql`. The sanctioned zero-setup channel is `uv tool install omniweave` or `pipx install omniweave`, both smoke-tested in CI. Trigger: a supported deployment target that cannot run `pip` |

> **Extends the charter.** The first three rows restate charter decisions; the installer row is new.
> The charter is silent on a standalone installer, and its rejection of vendored-Node platform wheels
> is on ordering grounds, so the same reasoning is applied here and the trigger is written down
> rather than left as an omission.

## 4. Versioning

### 4.1 The scheme

Three axes and nothing invents a fourth. [System architecture](02-architecture.md) §2 maps each axis
onto the five stability tiers; this section owns the declaration sites, the breaking-change
definitions and the support policy.

| axis | form | carried by | moves on | gate |
|---|---|---|---|---|
| `RELEASE` | one semver, e.g. `0.4.2` | thirteen of the fourteen distributions, the git tag `v0.4.2`, `writer_version` in `meta` | a normal release | **G5, CI job 1** |
| `CONTRACT` | a small int in `omniweave_core.contract` | the driver/target ABI — the only version a third party pins | a `RELEASE` **MINOR**, announced and migration-guided | **G16** |
| `SCHEMA` | two small ints in `omniweave_core.contract`, `SCHEMA` and `SCHEMA_MINOR`; the file's value in `index_state.schema` as `<major>.<minor>` | the L2 model and the store schema **together** | a migration; a major breaks a published read contract | migration tests, G27b |

`omniweave-ports` is the one exception to "one `RELEASE`": it is versioned by **Port major** (`1.0.0`
at release 1) because a driver pins it, and a driver that pinned `RELEASE` would pin the framework.
A driver never reads `CONTRACT` from a dependency bound; it declares what it supports on its card and
`activate()` checks it against `CONTRACTS_SUPPORTED` ([the driver system](04-driver-system.md) §5.3).

**`SCHEMA` has one code home and one disk home, and this paragraph states both.** The code home is
`omniweave_core.contract`, holding `SCHEMA` — the store-schema major this build writes — beside
`SCHEMA_MINOR`, its minor, which resets to `0` at a major bump; the pair is formatted
`f"{SCHEMA}.{SCHEMA_MINOR}"` at exactly one site, in that module. `omniweave_core.limits` holds no
version constant, now or ever ([system architecture](02-architecture.md) §2 rows 2 and 7). The disk
home is `index_state.schema`, one row, written `<major>.<minor>` as a string; **`meta` never gains a
`schema` key**, and `ow store verify` asserts that absence in its default check set rather than
comparing two copies. Settled by [ADR-9](adr/0009-schema-single-home.md) against charter erratum
`E72`; [the document model](03-document-model.md) §15.1 and [storage and
retrieval](07-store-and-retrieval.md) §3.1 name the same two homes, so no third document adjudicates
between them any more.

### 4.2 Every version-bearing site, and the tool that writes them

anydoc's five-location version gate is the mined precedent; `tools/check_versions.py` is CI job 1,
runs in ~2 s and fails before anything else starts. The count matters because "keep the versions in
sync" is unactionable and "40 strings across 18 files" is a checklist.

| class of site | count | value | written by `--set` | rewritten on a PATCH |
|---|---|---|---|---|
| `packages/<dist>/pyproject.toml` `[project] version`, `dist != omniweave-ports` | 13 | `RELEASE` | yes | yes |
| `packages/omniweave-ports/pyproject.toml` `[project] version` | 1 | Port major | yes | no |
| `omniweave-core ~= <M>.<m>.0` in the five `compile`-shipping dists plus `omniweave-serve` and `omniweave` | 7 | derived from `RELEASE` | yes | no |
| `omniweave-office ~= <M>.<m>.0` in `omniweave` | 1 | derived | yes | no |
| `omniweave`'s extras: ten single-sibling rows plus `recommended`'s three | 13 | derived | yes | no |
| `toolchains/{deck,video}/package.json` `version` | 2 | `RELEASE` | yes | yes |
| `tools/toolchains.toml` `[[toolchain]] version` per row | 2 | `RELEASE` | yes | yes |
| `omniweave_core/drivers/first_party.toml` `release` | 1 | `RELEASE` | generated in `build` (§7.2) | yes |
| **total version strings** | **40** | | across **18** files | **18** of the 40 |

Three further sites are **asserted and never written**: the git tag (`v<RELEASE>`, checked on a tag
push), `CHANGELOG.md`'s topmost heading (asserted to name `<RELEASE>`; hand-written, because a
generated changelog is a commit log), and `docs/reference/**` (generated by `ow surface emit --docs`
and byte-diff gated, so it carries `RELEASE` without declaring it). *(Build note, D973: `CHANGELOG.md` landed with its `0.1.0` section, hand-written. Before it, `tools/check_versions.py` filed the tag and heading assertions under the forty counted sites, so a checkout with a changelog printed 36/40 and a miscount warning. They are now reported apart, as "count toward no total" says.)*

Five `pyproject.toml` files contain **no** first-party version bound at all — `omniweave-office`,
`-pdf`, `-vision`, `-graph`, `-llm`, each depending only on `omniweave-ports >=1,<2`. That is rule 3
of the dependency rule showing up as an absence in a diff, and it is the property a reviewer should
check first when reading a new driver distribution's PR.

**`--set` is not the whole of step 2, and the missing half costs a cold CI run.** `uv.lock` records
every workspace member's version, so rewriting thirteen `[project] version` fields invalidates the
lock: `uv sync --frozen` would fail on the release commit with a lock/manifest mismatch, which is the
right failure and the wrong time to discover it. `check_versions.py --set` therefore runs
`uv lock --offline` as its last step and leaves the updated `uv.lock` in the same commit. The
consequence is arithmetic rather than an inconvenience: `hashFiles('uv.lock')` changes, all nine `uv`
cache keys miss, and the release run pays the ~95 s cold install in every one of its fifteen
uv-installing jobs (§6.6). That is where §6.3's "~25 min plus the approval pause" comes from — a
release run is always cold by construction, and the `restore-keys` prefix is the only thing keeping
it from being a full re-download.

### 4.3 What constitutes a breaking change, per public surface

| surface | version that moves | breaking (a MAJOR, or a `SCHEMA`/`CONTRACT` major) | not breaking |
|---|---|---|---|
| **document model schema** (`Block`, `Capabilities`, the wire keys, the digests) | `model_version` + `SCHEMA`, with `min_reader` raised | removing or retyping a field; reordering an enum's members (which is **forbidden**, not merely breaking); adding a `Kind` member (a MINOR that **raises `min_reader`**, so an old reader refuses rather than mis-reads) | adding an optional field with a new wire key; adding a `mark.kind`; adding a `payload` key (which bumps `digest_recipe` instead). See [the document model](03-document-model.md) §15.2 for the full table |
| **driver contract** (`omniweave_ports`, `CONTRACT`, the card grammar, `omniweave-driver/1`) | `CONTRACT`, on a `RELEASE` MINOR | removing or renaming anything in `omniweave_ports`; changing a Port protocol's signature; requiring a new card key; changing a wire frame's meaning; narrowing an accepted `card_schema` | adding a Port protocol; adding an optional card key inside `[capability.<port>]` (ignored with a recorded degradation — the one safe asymmetry); adding a `FailureClass` member; a new `RejectCode` row in `codes.toml` |
| **MCP tool shape** (`schema/mcp-tools-v1.json`, the `instructions` string) | `RELEASE` MAJOR | removing a listed tool; renaming an `mcp_name`; adding a **required** input property; removing an output property; narrowing an input enum; changing a tool's read-only/idempotent/open-world bits | adding a tool; adding an optional input property; widening an enum; changing a `summary` or `decision` clause; moving a tool between `listed` and `enabled` (an operator-visible config change, disclosed) |
| **CLI** | `RELEASE` MAJOR | removing a verb or a group; removing a flag; changing an exit code's meaning; changing a `--render json` document's shape incompatibly; renaming a group (there are no aliases, so a rename is a removal) | adding a verb, a group at three or more verbs, or a flag; adding a field to a `--render json` document; changing human-readable text |
| **SDK** (`omniweave.sdk`) | `RELEASE` MAJOR | removing a method or an attribute that [interfaces](10-interfaces.md) §9.4 classifies `@stable`; changing a parameter's type or making one required; returning a list where an iterator was returned (or the reverse — `Doc` is a lazy handle by contract). **A `@provisional` symbol is the one carve-out:** it may be changed or removed on a `RELEASE` MINOR with a changelog entry and a one-MINOR deprecation shim, and an `@internal` symbol carries no promise at all — §9.4 owns which symbol is which, and `omniweave/sdk/_generated.pyi` is byte-diff gated so the tier is checked in the same PR as the change | adding a method, a keyword argument with a default, or an attribute; tightening a type annotation that was already accurate |
| **index format** (the `.owstore` `[SOR]` set, the `.owdoc` envelope) | `SCHEMA` major / `container_version` | dropping or retyping an `[SOR]` column; changing an `[SOR]` view's columns; changing a `.owdoc` member layout (that is `container_version`, not `SCHEMA`) | adding a table, a column or an index; adding or rebuilding a `[DER]` object; adding an archive member. See §5 |
| **packaging** (the distribution set, the extras map, the entry-point groups) | `RELEASE` MAJOR | removing a distribution from `first_party.toml`; removing an extra; renaming a distribution; changing an extra's target sibling | adding a distribution; adding an extra; raising a `weights.toml` ceiling with a `why` line; changing a third-party constraint that resolves to the same closure |

Two rules that cut across all seven rows:

1. **A generated artefact never breaks on its own.** Every agent-facing surface is generated from one
   `ActionSpec` (INV-20) and byte-diff gated (G25), so an MCP break, a CLI break and an SDK break are
   the same change to the same declaration. That is what makes those three rows consistent by
   construction rather than by review.
2. **A driver's `schema_version` is the only driver version in a cache key, and forgetting to bump it
   is the most expensive single mistake available in this design** — it serves stale billed output
   forever with no symptom. Defences: review, a testkit check that diffs output across two tagged
   versions, and `ow cost --by driver --since 7d` showing a driver's spend fall to zero after a
   release. The last is a lagging indicator that requires someone to look, and the charter says so.

### 4.4 Support policy and cadence

| what | supported | mechanism |
|---|---|---|
| `RELEASE` | the current MINOR and the one before it get fixes; older get nothing | branch `release/<MAJOR>.<MINOR>` cut at the tag; a fix is cherry-picked, never developed there |
| `CONTRACT` | the previous **two** releases' drivers load against HEAD | **G16** builds the conformance-template driver from each of the last two tags and loads it against HEAD; a failure blocks the merge |
| `SCHEMA` | a two-release deprecation window before a major | announced like a `CONTRACT` bump; `[DER]` objects are explicitly outside the promise |
| Port major | `omniweave-ports >=1,<2` for the life of Port 1 | a Port 2 is a new distribution version, and Port 1 drivers keep resolving until the framework drops `CONTRACTS_SUPPORTED` support for them |
| Python | 3.11, 3.12, 3.13 tested; **no upper bound** in `omniweave-core` or `omniweave` | an upstream ceiling lives in the distribution that owns it, never in core |
| SQLite | `MIN_SQLITE = (3, 42, 0)`; below it `store/sqlite.py` **refuses at open**, naming `pip install omniweave-core[sqlite]` | `RETURNING` needs 3.35, STRICT needs 3.37, `unixepoch()` needs 3.38 and `unixepoch('subsec')` needs 3.42, and shipped DDL uses all four |

**G16 must not reach the network, and the mechanism is the reason.** Building "the previous two
releases' template drivers" from PyPI would put an index fetch on the PR path, would fail on a fork
PR with a restricted token, and would let a yanked release break an unrelated merge. G16 instead adds
a `git worktree` at each of the last two tags, builds `omniweave-conform` from source there with
`uv build --package omniweave-conform`, scaffolds the template driver from that checkout's own
`ow drivers scaffold`, and loads the result against HEAD. Nothing is downloaded, the two tags are
already in the clone (which is why the `conform` job checks out with `fetch-depth: 0`, §6.2), and the
gate is reproducible from any commit that has the history.

**Cadence is derived, not chosen.** A MINOR every six weeks, PATCH as needed. The number falls out of
the two policies above: a field deprecation is three phases over two `RELEASE` minors and no phase is
skippable, and support covers the current MINOR plus one. At six weeks a deprecation completes in
about twelve weeks and a consumer who upgrades once a quarter never skips a supported window. At six
months a deprecation takes a year and `CONTRACT`'s two-release window becomes a two-year promise G16
must keep; at two weeks the same window is six weeks, which is shorter than a downstream driver
author's typical response time. Neither extreme is a schedule, it is a contract length.

A field is deprecated in three phases over two `RELEASE` minors — announce (every write emits
`Degradation(kind="deprecation")`, so the operator learns by running rather than by reading a
changelog), stop writing, then remove at the next `model_version` MAJOR with the wire key retired into
`tools/wirekeys.toml` and **never reused**. [The document model](03-document-model.md) §15.4 owns that
mechanism; the release-engineering half is that phase 1 and phase 2 must land in *different* releases,
which `tools/check_versions.py` cannot verify and a reviewer must — so the PR template asks for the
phase explicitly (§8.4).

## 5. The index format version and its migration path

The index format version is `SCHEMA`, and it is **not** the software version. A given `RELEASE` reads
a range of `SCHEMA`s and writes exactly one; a given `.owstore` records the one that wrote it. Nine
on-disk version fields exist. Their semantics are owned elsewhere — [the document
model](03-document-model.md) §15.1 for the L2 and archive fields, [storage and
retrieval](07-store-and-retrieval.md) §3.1 for the store's compatibility table — and what this table
adds is the release-engineering column: which of them a release may move, and what moving it costs.

| field | where the file carries it | may a release move it? | cost of moving it |
|---|---|---|---|
| `SCHEMA` | `index_state.schema` as `<major>.<minor>` | minor: freely, additive DDL only. major: two-release window | a migration; a major is a published read-contract break over the `[SOR]` set |
| `container_version` | `meta`, `manifest.json` | yes, with a `min_reader` review | old readers refuse the archive at a MAJOR |
| `model_version` | `meta`, `doc.model_version`, `manifest.json` | yes | see the §4.3 row; a MAJOR is a two-release window |
| `min_reader` | `meta`, `manifest.json` | raised by any additive change an old reader would mis-read | old readers refuse rather than mis-read; this is the point |
| `digest_recipe` | `meta`, `manifest.json` | **at most annually** | invalidates every content-addressed cache in the fleet; serviced by `op.redigest` over every generation present, never a re-parse |
| `segment_recipe` | `meta` | **at most annually** | `op.resegment` over stored blocks |
| `scorer_version` | `index_state` | freely | every cached fused score is invalid; the retrieval planner refuses a stale one |
| `graph.resolve_signature` | `meta` | freely | `entity_band` is rebuilt at the top of the next resolve pass |
| `writer_version` | `meta` | every release, mechanically | nothing — **forensics only, never a compatibility input** |

At release 1: `SCHEMA = 1`, `model_version = "1.1"`, `container_version = "1.0"`, `min_reader = "1.0"`,
`digest_recipe = 1`, `scorer_version = 1` ([the document model](03-document-model.md) §15.1).

`writer_version` is the field a release-engineering reader should notice. It is the only one that
moves on every release and the only one nothing reads for a compatibility decision, which is exactly
why it exists: when a corpus behaves oddly, "which build wrote this" is the first question and
`RELEASE` is the only answer that identifies a commit, a workflow run and a set of signed artefacts.

### 5.1 Migrations ship in the wheel, not in a tool

`schema/migrations/*.sql` is packaged with `omniweave-core` as package data, read through
`importlib.resources` at use time (§2.6), applied forward-only in numeric order, one transaction
each. Naming is `NNNN_<slug>.sql`, four digits, and the order is load-bearing: `0002_graph.sql`
precedes `0003_index.sql` because L4 indexes and foreign keys reference L3 tables, and the reverse
ordering was a real defect — an index on a table a later file creates aborts the migration and
**neither file applies** ([storage and retrieval](07-store-and-retrieval.md) §3). A view survives a
forward reference lazily; an index and a foreign key do not. Gate G27(b) applies every migration in
numeric order to an **empty file** on the declared `MIN_SQLITE`, which is the only test that catches
it.

**G27(b) then asserts, at the end of the run and not after `0001_init.sql`, that `index_state` and
`meta` are each in exactly one home.** After `0001` → `0005` have applied in order, `index_state`
holds exactly one `schema` row whose value equals `f"{SCHEMA}.{SCHEMA_MINOR}"` read from
`omniweave_core.contract`, and `meta` holds no `schema` key at all. The anchor is the end of the run
because `index_state` is created by `0003_index.sql` — an assertion written against `0001_init.sql`
is unrunnable, since the table does not yet exist. §4.1 states the two homes;
[ADR-9](adr/0009-schema-single-home.md) rules them, and `ow store verify` checks the same absence on
a real store rather than comparing two copies.

Three release-engineering rules follow from "in the wheel" rather than "in a tool":

1. **The migration set is append-only against the previous tag**, checked the same way `codes.toml` is
   (G13's mechanism, G27b's assertion). Editing a shipped migration in place is unfixable: some
   stores have applied it and some have not, and `migration.version` cannot distinguish them.
2. **A migration may not import anything outside `omniweave_core`**, because it runs from a wheel
   whose only dependency is `omniweave-ports`. A backfill that wanted a third-party parser would make
   the migration path violate INV-2; the answer is a `work`-queue pass, not a dependency.
3. **The `0001_init.sql` file is where a `NOT NULL` column with a default belongs.** Three binding
   `ALTER TABLE … ADD COLUMN … NOT NULL` statements are not universally illegal — verified on SQLite
   3.45.1, they raise only against a **non-empty** table — but a later migration adding one succeeds
   on a fresh store and fails on every populated one, which is the worst possible distribution of
   outcomes. Ship the column in `0001_init.sql` or backfill it in two steps.

Every migration row in the `migration` table declares three things a later operator needs and cannot
re-derive: its `cost_class` (`ddl` / `backfill` / `rebuild`), whether it is `resumable`, and
`unbackfilled_means` — required prose that `ow doctor` prints **verbatim**. A migration whose
estimated row-touch exceeds `WATCHDOG_MS / 2` **must** set `resumable = 1` and run through the `work`
queue; codegraph's recorded scar is 79 s of `CREATE INDEX` against a 60 s watchdog, SIGKILLed *after
doing the work*, so the next start redid it. See [storage and
retrieval](07-store-and-retrieval.md) §3.8 for the table and the resumption semantics.

### 5.2 Allocating a migration number under concurrent pull requests

This is the hard half of "append-only", and it is the one place where a register that is provably
correct on every PR in isolation is wrong the moment two of them merge.

**The failure.** Two PRs branch from the same commit. Each adds `0004_*.sql` — different slugs,
different content. Each passes G27b in isolation, because on an empty file a single `0004` applies
cleanly. The first merges. The second merges. `schema/migrations/` now holds two files numbered 0004,
and `migration.version` is `INTEGER PRIMARY KEY`, so applying both inserts version 4 twice and the
second raises a constraint violation — on every store in the fleet, at ingest time, after the first
one has already committed its DDL. The gap case is quieter and worse: PRs adding `0004` and `0006`
with `0005` never landing produce a set that applies fine to an empty file and applies *out of
intended order* on a store that received `0006` in an earlier release and `0004` in a later one.

**The mechanism, in three parts, none of which is optional.**

1. **G27b asserts density and uniqueness, not just applicability.** `tools/gate_migrations.py` reads
   the numeric prefixes of `schema/migrations/*.sql`, asserts they are exactly `1..N` with no
   duplicate and no gap, and only then applies them in order to an empty file on `MIN_SQLITE`.
   Duplicates would also surface from the `migration` primary key during that apply — which is a
   pleasing redundancy and not a substitute, because a gap raises nothing.
2. **Branch protection requires branches to be up to date before merging.** That single setting is
   what moves the collision from after the second merge to before it: the second PR must rebase onto
   the first, its `0004_*.sql` becomes `0005_*.sql`, and CI re-runs on the rebased head. The cost is
   one extra CI run per PR whenever the base moves under it — roughly 11 minutes of runner time —
   and it is the price of every append-only register in `tools/`, not just this one.
3. **Squash-only merges keep the append-only diff computable.** G13 compares `codes.toml` against the
   previous tag; an append-only check over a merge commit's ancestry is ambiguous in a way one over a
   linear history is not. §8.3 states the rule; this is the reason it is not taste.

**The same three parts cover five other registers**, and stating them once is the point: `codes.toml`
(G13), `tools/gates.toml`, `tools/invariants.toml`, `tools/wirekeys.toml` and `tools/events.toml`
(G20) all allocate an identifier that two branches can allocate identically. Every one of them is
protected by exactly the mechanism above, and no one of them needs its own scheme.

**The boundary that decides whether renumbering is legal is the tag, not the merge.** A migration
that has only ever existed on a branch is renumbered freely, because no store has applied it. A
migration that has appeared in a published release is never renumbered and never edited, because some
stores have applied it and `migration.version` cannot tell which. `gate_migrations.py` therefore
diffs against the previous tag, not against the previous commit: renaming `0004_a.sql` to
`0005_a.sql` inside one release cycle passes, and renaming a file that the previous tag contains
fails with the tag named.

```text
$ python tools/gate_migrations.py
G27b FAIL  schema/migrations/ has two files numbered 0004:
             0004_anchor_akind.sql   (in v0.4.1, PUBLISHED — never renumber)
             0004_segment_cover.sql  (new on this branch)
           migration.version is an INTEGER PRIMARY KEY, so both would insert version 4 and the
           second would abort on every store that applied the first.
           fix: rebase on the default branch and rename the NEW file to 0005_segment_cover.sql.
           Do not touch 0004_anchor_akind.sql: v0.4.1 shipped it.
```

### 5.3 What an operator actually runs, and what happens if they do not

```text
$ ow store migrate --dry-run
  corpus handbook   .omniweave/index.owstore
  written by        RELEASE 0.3.1 · SCHEMA 1.4 · model_version 1.1 · digest_recipe 1
  this binary       RELEASE 0.4.0 · SCHEMA 2.0 · writes model_version 1.2
  pending           0004_anchor_akind.sql   ddl        not resumable   ~0.2 s
                    0005_segment_cover.sql  backfill   RESUMABLE       ~14 min over 812k segments
                    unbackfilled_means: "a segment with cover_bits IS NULL has not been
                    covered by any pass in this generation; retrieval treats it as uncovered
                    and the corpus card counts it as a coverage gap."
  after             SCHEMA 2.0 · model_version 1.2 · digest_recipe 1 (unchanged, no re-digest)
  reversible        NO. Take a backup first: ow store backup <path>
                    VACUUM INTO needs free space equal to the store; this store is 41 GB.
$ ow store migrate
```

`ow store migrate` is the explicit verb and there is no bypass flag. It is not, however, the only path
that advances `SCHEMA`, and getting that wrong is the difference between a design and a wish: [storage
and retrieval](07-store-and-retrieval.md) §3.1 is authoritative and says a store below the reader's
version **migrates forward on an exclusive write open**, while a `mode=ro` open **refuses** and names
`ow store migrate`. So the real behaviour is a two-by-two:

| open mode | file below the reader | file above the reader |
|---|---|---|
| write (`ow ingest`, `ow index`) | migrates forward, in the ingest's own transaction sequence | refuses: `OW-S-030` / `OW_SCHEMA_AHEAD`, naming both versions and `pip install -U omniweave-core` |
| read-only (`ow query`, MCP, a hook) | **refuses** and names `ow store migrate` — a read must never mutate the file whose mtime the freshness check reads | refuses, same code |

The release-engineering consequence is the one this document owns: because the *ingest* path migrates,
a long `backfill`-class migration is charged to whoever runs the next ingest, not to whoever ran the
upgrade. That is why `resumable = 1` above `WATCHDOG_MS / 2` is mandatory rather than advisory, why
`unbackfilled_means` is required prose, and why checklist step 8 (§7.6) is a release-blocking check
rather than a note. `ow doctor` prints pending migrations before any of this happens, so the operator
can choose to pay the cost deliberately.

> **Extends the charter.** `ow store migrate --dry-run` is new here. `ow store migrate`,
> `ow store backup` (a `VACUUM INTO`) and `ow doctor` are all named by [storage and
> retrieval](07-store-and-retrieval.md); a plan-print flag is not. It exists because the cost figure
> and the `unbackfilled_means` prose above are the whole basis for an operator's decision to take a
> 41 GB backup, and printing them only *during* the migration is printing them too late.

### 5.4 The refusal matrix, store side

[The document model](03-document-model.md) §15.2 owns the archive-side forward-compatibility table
(`model_version` MAJOR, `min_reader`, unknown fields, unknown `Kind`, unknown archive members). Three
store-side rows are this document's, because each is a packaging or release decision rather than a
model one:

| situation | what happens |
|---|---|
| `SCHEMA` **minor** above the reader's, same major | **serves reads**: unknown `[DER]` objects are ignored and unknown `[SOR]` columns are not selected. **Writes refuse** — a writer that does not know a column cannot maintain its invariant |
| a `digest_recipe` mismatch | not a refusal: `op.redigest` recomputes from **stored fields**, over every generation present, not only the head |
| an open **Bulk window** marker at store open | **refuses to serve** (`OW-S-031`) and names `ow store repair` — secondary indexes and FTS triggers may be dropped, so a query would silently under-return |

The middle row is the one that makes an annual `digest_recipe` budget a *release-planning* fact rather
than a runtime one: two recipe bumps in one calendar year is a process failure, and checklist step 7
is where it gets caught.

### 5.5 Downgrade, and the honest answer

**A `SCHEMA` downgrade is not supported and no migration is reversible.** The supported paths are a
restore from `ow store backup`, or `rm -rf .omniweave` and re-ingest — which is a documented, lossless
operation because the only committed store artefact is `omniweave.index.lock`, the index's *receipt*
rather than the index. Re-ingest is not free (`retain_parts`, the call cache and the blob CAS decide
how much of it is CPU rather than a re-bill), but it is always available, and keeping that sentence
true is a constraint every rule in [storage and retrieval](07-store-and-retrieval.md) is subordinate
to.

Two things a downgrade story must not pretend. A backup taken with `VACUUM INTO` needs free space
equal to the store, so on a multi-tens-of-GB corpus "take a backup first" is a capacity request and
`--dry-run` prints the number. And `pip install "omniweave==<older>"` after a migration produces the
`OW_SCHEMA_AHEAD` refusal, not a degraded read — which is correct, and is why the release note for any
`SCHEMA`-moving release leads with it.

## 6. CI

### 6.1 Two workflow files, and why

`.github/workflows/` holds exactly two files: `ci.yml` and `release.yml`. `release.yml` invokes
`ci.yml` through `workflow_call`, so **the release gate *is* CI** and the two cannot diverge. The
comparison worth making is local-deep-research, which runs **66** workflow files including a
`release-gate.yml` that re-declares checks already present on the PR path, and which therefore has to
maintain two definitions of "passing". The cost of two files is real and accepted: no per-check status
badges, and a re-run re-runs everything.

The single-file publish path also removes an entire class of defect by construction, and the
mechanism is subtle enough to state precisely. PyPI Trusted Publishing matches the OIDC `workflow_ref`
claim, and that claim names the **caller** when a workflow is invoked through `workflow_call` — so a
reusable *publish* workflow fails with `invalid-publisher`
(`pypa/gh-action-pypi-publish#166`, `pypi/warehouse#11096`, both cited in
`local-deep-research/.github/workflows/release.yml:1482-1490`). local-deep-research's workaround is
`repository_dispatch` from `release.yml` to `publish.yml`, and `repository_dispatch` runs on
**default-branch HEAD at dispatch time**, not on the release commit. Their own header comment records
the consequence exactly (`publish.yml:8-14`): *"repository_dispatch runs on default-branch HEAD at
dispatch time — NOT the release commit. The `release` env approval is human-paced, so main can move
between the release commit and the dispatch (on v1.9.0 it was 4 PRs ahead, and PyPI shipped code
absent from the tag/Docker image)."* Their fix is `client_payload.sha` plus a fail-closed check that
the value is a full 40-hex SHA, in POSIX `sh` because the validating job runs in an Alpine container.

omniweave has no `repository_dispatch`, and the reason the drift cannot recur is not that dispatch is
avoided but that **the human approval pause happens inside the run, on `github.sha`**: the publish job
declares `environment: release`, so the run stops at that job with every artefact already built from
the tagged commit, and no amount of human latency can move the commit under it. `ci.yml` stays
reusable because it does not publish; the constraint is only on the job that calls
`pypa/gh-action-pypi-publish`, which is a top-level job in `release.yml`. `release.yml` additionally
asserts `github.ref_type == 'tag'` and that the tag's commit is an ancestor of the default branch.
What the pause does *not* survive for free is artefact retention, and §7.4 is that problem.

> **Extends the charter.** `incremental` and `crash` are new job rows. The charter's CI inventory
> lists eight jobs and separately assigns G19 a 300-document fixture in 40 scripted mutations and G21
> a kill-9 matrix — neither of which fits inside `golden`'s <= 4 min budget. Giving each its own job
> preserves both the gate's numbers and `golden`'s budget; shrinking the fixture to fit would have
> changed a gate the charter says owns its two numbers. `build`'s budget rises from 4 to 6 min for
> the second build pass and the three wheelhouse installs (§6.6).

**`ci-ok` is the one required status check, and its implementation is where a naive version fails
silently.** `toolchains` is conditional on the paths a PR touches. A conditional job that does not run
reports `skipped`, and GitHub cannot require a check that may never report — a required
`toolchains` would block every PR that does not touch TypeScript, forever. So there is exactly one
required check, `ci-ok`, and it runs `if: always()` and inspects the `needs` context rather than
relying on the implicit `success()`:

```yaml
  ci-ok:
    needs: [versions, gates, test, golden, conform, incremental, crash, parity, toolchains, build]
    if: always()
    runs-on: ubuntu-latest
    steps:
      - name: assert every job succeeded, and that only toolchains may be skipped
        env:
          NEEDS: ${{ toJSON(needs) }}
        run: python3 tools/ci_ok.py    # SKIPPABLE = {"toolchains"}; anything else skipped is a fail
      - name: print the quarantine list
        run: python3 tools/print_quarantine.py    # §6.8; visible on every PR, not on request
```

Three properties of that job are the `[[job_assertion]]` `ci-ok.skips_declared`. Every entry in
`needs` must be `success` or, for `toolchains` alone, `skipped`. A `cancelled` result is a failure,
not a pass, because `if: always()` also fires on cancellation and a bare truthiness check would treat
an aborted matrix as green. And the allowlist is a literal set in `tools/ci_ok.py`, not a wildcard, so
adding a second conditional job is a reviewable act rather than a silent widening.

**Checkout depth is part of the gate contract, not a performance knob.** `actions/checkout` defaults
to `fetch-depth: 1`, and three gates read history: G13 diffs `codes.toml` against the previous tag,
G27b diffs the migration set against the previous tag (§5.2), and G16 builds template drivers from
the previous two tags (§4.4). Those jobs check out with `fetch-depth: 0` and `filter: blob:none`, a
blobless clone that fetches file contents on demand — the repository's largest tracked tree is
`fixtures/` at ≤ 64 MB, so the full-history clone is cheap and the blob filter keeps it that way.
Every other job uses `fetch-depth: 1`. Getting this wrong does not produce a wrong answer; it
produces `fatal: no such ref` in a gate whose failure message is about error codes, which is worse
than either.

**The matrix axes, in full.** `{OS} × {Python}` is the charter's nine cells. The third axis — extras —
is not a cross product, because a nine-by-eleven matrix buys nothing: the install profiles differ in
what is *installed*, and installation is what `build` and `parity` test. *(Build note, D883, a user ruling of 2026-10-19: the Python floor is 3.12, so the table's Python row now reads 3.12, 3.13, 3.14, and every single-cell job (`gates`, `golden`, `conform`, `incremental`, `crash`, `build`) runs 3.12. 3.11 could never pass: it rejects the `MappingProxyType` dataclass defaults the packages use (about 260), and `atheris` 3.1.0 ships no cp311 wheel. | trigger | jobs | blocks | budget |

The tag row's ~25 min is a **cold** number by construction, not a pessimistic one: checklist step 2
rewrites thirteen `[project] version` fields and therefore `uv.lock`, so `hashFiles('uv.lock')`
misses every `uv` cache key on the release commit (§4.2). A release run never gets a warm cache and
budgeting one would be a planning error.

`concurrency: { group: ci-${{ github.ref }}, cancel-in-progress: true }` is set on `ci.yml` and
**not** on `release.yml`. On a PR, a second push should cancel the first run: at 17 concurrent jobs
whose budgets sum to `1×20 s + 1×180 s + 9×240 s + 240 + 300 + 480 + 300 + 600 + 180 + 360 ≈ 4,820`
runner-seconds, a superseded run wastes on the order of an hour of runner time and, worse, competes
for the same cache keys. On a tag, cancellation would abandon a partially published release, which
§7.7 says is the one state with no clean recovery.

is the argument [risks](17-risks.md) §1.1 made for its own register and
[ADR-2](adr/0002-invariant-and-gate-registers.md) adopted for this one.

split. The **hard** assertion is on a deterministic quantity: the module count from
`python -X importtime -c "import omniweave_core"`, and the module count on the hook path. A module
count does not vary with runner load and it is what actually regresses — a new eager import. The
wall-clock assertion is a **25% band** against `eval/baselines/coldstart-<os>-<py>.json`, best-of-five
after two warm-up runs, and the runner label is pinned in the workflow (a **Runner class pin**), so a
GitHub runner-image change shows up as a single deliberate re-bless in `eval/BLESS.log` rather than as
nine mysterious failures. OQ-4 records that the 25% number is inherited, not measured.

The nightly `ow-gpu-1` cell is the only place `omniweave-vision` is installed in CI. Every other cell

`OW-Q-004` and never a live call. That is what keeps nine test cells free of a multi-gigabyte download
and makes a model-dependent test reproducible at all.

The weekly wheel scan is the one job that can fail for a release nobody has touched, and it is the
only defence against the failure mode local-deep-research's `pyproject.toml` comments are entirely
built around: *"1.12.0 is the reviewed floor: never resolve below it, and re-check the parser contract
and its tests before raising the ceiling."* A floor with a CVE comment is only useful if something
re-reads it after the CVE that motivated it is superseded.

### 6.6 Caching, and the budget it has to fit in

Cache correctness matters more than cache hit rate here, because two of these caches can make a gate
pass for the wrong reason.

| what | key | scope | why that key |
|---|---|---|---|
| the `uv` cache | `uv-${{ runner.os }}-py${{ matrix.py }}-${{ hashFiles('uv.lock') }}`, with `restore-keys: uv-${{ runner.os }}-py${{ matrix.py }}-` | every Python job | a lock change invalidates exactly one key, and the prefix fallback turns it into a partial hit rather than a cold miss. `uv sync --frozen` then fails on a stale lock rather than resolving around it — which is the gate lockfile drift cannot slip past |
| the `pnpm` store | `pnpm-${{ hashFiles('toolchains/pnpm-lock.yaml') }}` | `toolchains` only | the only job with a Node runtime |
| the Tier-B golden corpus | `golden-${{ digest from eval/corpora.toml }}` | `golden`, nightly | keyed by **digest, never by version or date**, so a corpus refresh is a new key and a poisoned cache is impossible. A digest mismatch on use is a permanent failure that never triggers a fetch |
| `schema/expected/` renders | not cached | — | they are committed; caching a golden is caching the answer |
| the probe verdict cache (`$OMNIWEAVE_HOME/probe/`) | **never cached** | — | a stale probe verdict is precisely the bug the probe exists to catch. `OMNIWEAVE_HOME` is a fresh temp directory per job, except that the digest-named golden directory is symlinked in |
| Cassettes | not cached | — | committed under `fixtures/cassettes/`, content-addressed, and small |
| pre-commit environments | `precommit-${{ hashFiles('.pre-commit-config.yaml') }}` | the developer's machine, not CI | CI runs the gates directly; pre-commit is a convenience |

**A fork PR reads the base branch's caches and cannot write them, which is why the golden corpus is
digest-keyed and not name-keyed.** GitHub scopes cache writes to the branch, so a fork cannot poison a
key the default branch will read — but it *can* read one, so anything cached must be safe to hand to
untrusted code. Every entry above is either public upstream content (`uv`, `pnpm`) or
content-addressed and re-verified on use (the golden corpus). Nothing that a gate asserts about is
cached at all, which is the next rule.

**The cache has a hard ceiling and this design can exceed it, so the arithmetic is written down.**
GitHub Actions gives a repository 10 GB of cache with LRU eviction and no warning when it evicts. One
lockfile generation costs nine `uv` keys (3 OS × 3 Python) at an **estimated** ~400 MB each, plus the
pnpm store at ~150 MB and the golden corpus at ~240 MB — call it 4.0 GB. Two live generations fit; a
third does not, and the symptom is not an error but every job silently taking the ~95 s cold path.
Three mitigations, in order of effect: the `restore-keys` prefix above, so a new lock generation
starts from the previous one instead of from nothing; the weekly prune job in §6.5, which is what
bounds the number of live generations to "the default branch plus the open PRs"; and keeping the
golden corpus out of the per-cell keys by symlinking one digest-named copy. The 400 MB figure is an
estimate and the number that replaces it is `gh cache list --limit 200 --json key,sizeInBytes` after
one week of real traffic (OQ-8).

**The install times are targets, not measurements.** `uv sync --frozen --all-packages --group dev` is
budgeted at **~95 s cold** and **~12 s warm**, which is what makes the PR wall clock ~17 min cold and
~11 min warm. Fifteen of the nineteen jobs install through `uv` (`toolchains` uses pnpm, `parity`
installs inside its container, and `versions`/`ci-ok` install nothing), so the cache saves roughly
15 × 83 ≈ 1,245 runner-seconds per PR run. The nine `test` cells are 747 s of that, which is why they
get their own key per Python version rather than sharing one.

**Every job budget in §6.2 is enforced, and the enforcement is deliberately two-sided.** Each job
carries `timeout-minutes` at **twice** its stated budget — a hard stop that turns a hung `parity`
container into a 20-minute failure rather than a six-hour one — and each job writes its wall time to
the Counter `ci.job_seconds.<job>`, which ratchets in `eval/counters.toml`. The hard timeout catches a
hang; the ratchet catches the slow accumulation that never trips a timeout and turns an 11-minute PR
into a 25-minute one over two quarters. A budget with only the first is a budget nobody reads. *(Build note, D962, a user ruling of 2026-10-23: the `test` job's Windows cells carry 60 minutes and its Linux and macOS cells 45 (D886's figure). Windows cells run 30-40 minutes, and a queue of concurrent runs pushed them past 45, so GitHub cancelled T3 mid-run on #206 and on master's merge of #218, every rerun passing. G16's `git` calls wait 300 s, not 120: `git worktree add --detach` of a tag timed out twice on windows-latest under `-n auto`.)*

**That row declares `source = "ci"`**, the fourth member of the `source` vocabulary every
`eval/counters.toml` row carries — `{manifest, route_spend, driver_observation, ci}`,
[quality](13-quality.md) §2.8's schema and sole home. `Q-G5` compares only the three run-sourced
classes against their sources, and a `source = "ci"` row never reaches `eval_counter` or
`eval_scoreboard`: that table's primary key is `(run_id, counter, scope)` with `run_id NOT NULL`,
and a counter measuring a CI job has no run to reference. `ci.job_seconds.<job>` is the first and, at
release 1, the only `ci` row ([ADR-11](adr/0011-eval-register-reconciliation.md)).

**The `build` job's four steps, in order, because the order is the mechanism.**

1. `SOURCE_DATE_EPOCH=$(git show -s --format=%ct HEAD)` then `uv build --all-packages` → 28 files.
2. `tools/gen_first_party.py --dist dist/ --release <R>` writes
   `packages/omniweave-core/src/omniweave_core/drivers/first_party.toml` from the 26 non-core files'
   sha256s, then core alone is rebuilt (§7.2).
3. `uv build --all-packages` a second time into a scratch directory and diff all 28 sha256s against
   step 1 for the 26, and against step 2 for core's two — the `build.reproducible` job assertion. A
   non-reproducible wheel means SLSA provenance names a digest nobody else can produce, and §7.4
   shows the second thing it buys.
4. `uv pip download` the third-party closure of `omniweave[recommended]` and of
   `--all-packages` minus vision into `wheelhouse/`, copy `dist/*` in, then
   `pip install --no-index --find-links wheelhouse …` for each of §2.4's three install profiles into
   fresh venvs. Offline is load-bearing: with an index reachable, a sibling constraint could be
   satisfied by a *previously published* wheel and a broken `dependencies` entry would pass.

Two anti-patterns refused outright. **No dependency-updating bot commits.** The nightly `uv lock
--upgrade` runs as a *report*, not a commit, because a lock bump is a change to the reproducibility
basis of every golden and every cache key, and it needs the same review a code change gets. And **no
cache of anything a gate asserts about**: a cached `NOTICE`, a cached `schema/` render or a cached
weight measurement would each make its gate pass by remembering the previous answer.

### 6.7 The tools CI runs that are not in the dev group

[System architecture](02-architecture.md) §3.3 fixes the dev dependency group at exactly the ten
packages the charter prints, and gives the reason: introducing an import-graph linter would put a
package's own import graph between HEAD and the gate that proves HEAD's import graph. That rule is
right and it leaves a hole this document has to close, because CI demonstrably runs seven executables
that are not in the group. Where they come from is a supply-chain question with a written answer.

**The rule.** A tool CI runs is either (a) a SHA-pinned GitHub Action with the version in a trailing
comment, or (b) a `uvx <name>==<exact version>` invocation in a `run:` step. There is no third
channel: no `pip install` without `==`, no `curl | sh`, no unpinned `npx`, and nothing installed into
the workspace environment. The `[[job_assertion]]` `gates.workflow_tools_pinned` reads both workflow
files and asserts both halves — zizmor covers the `uses:` half as a linter, and a ~40-line check
covers the `run:` half, because zizmor does not read shell.

| tool | channel | serves | job |
|---|---|---|---|
| `zizmor` | `uvx` | linting the workflows themselves: unpinned `uses:`, `persist-credentials`, template-injection sinks | `gates` |
| `pip-licenses` | `uvx` | G3's resolved-graph scan (§9.4) | `gates` |
| `trivy` | action | the SPDX and CycloneDX SBOMs, one pair per install profile | `release` |
| `syft` | action | the container image's per-arch SBOM | `release` |
| `cosign` | action (`sigstore/cosign-installer`, `cosign-release: 'v2.6.3'`) | `sign-blob` and `verify-blob` | `release` |
| `slsa-verifier` | `uvx` | the `docs/verify.md` round-trip in checklist step 15 | `release` |
| `gh` | preinstalled on the runner | the previous release's SBOM for §7.3 rule 4's floor | `release` |

Two honest limits. `uvx` resolves from PyPI at job time, so a `gates` run is not reproducible against
a deleted or yanked tool version — acceptable for a gate tool, which fails loudly and blocks nothing
but the PR, and unacceptable for a runtime dependency, which is why the split exists at all. And
`zizmor` is the workflow people forget: the CI definition is itself an attack surface with write
access to the release, and local-deep-research runs `zizmor-security.yml` for exactly that reason.

### 6.8 What is deliberately not a gate

**Three things are explicitly not gates, because a warning that cannot fail is the thing that rots.**
There is no `--warn-only` anywhere. A check that cannot yet fail is either quarantined as
`informational` with an issue number (the flake path, below) or it is not in CI. `EvalStatus` has no
`pass_with_warnings` for exactly this reason, and the eval `unknown` state is never a pass:
`ow eval release-check` refuses on it.

**Flake policy, with a number.** `eval_flake` records runs, failures and rerun-green counts per
`(test_id, day)`. Above **2% over 30 days** a test is quarantined to `informational` with a mandatory
issue link (Q-G18). A quarantined test still runs and still reports; it just cannot block. The
quarantine list is printed in the `ci-ok` job's summary (§6.2), so its length is visible on every PR
rather than discoverable only by reading a config. [Quality](13-quality.md) owns the `eval_flake`
table and the quarantine semantics; what this document owns is that the list is rendered where a
reviewer cannot avoid seeing it.

**A gate that is itself wrong is a real failure mode and it has a procedure.** Every `G<n>` row in
`tools/gates.toml` carries an owner and a review date, exactly as `eval/gates.toml`'s metric rows do.
A gate believed wrong is not disabled and not made `--warn-only`; it is either fixed in the same PR
as the code, or its row is amended by an ADR that quotes the old assertion and the new. graphify's
own architecture test shows why a gate needs a guard on itself: `test_the_table_was_actually_parsed`
asserts the row regex matched at least ten symbols and that three specific modules are among them,
*"guard the parser itself: a regex that silently matches nothing would make every parametrized test
below vacuous."* Every gate here that discovers its own inputs — G27's document walk, G4's `ast`
walk, G8's semgrep run — carries the same guard: an assertion on the count of things it found.

**The data artefacts' container is settled, and the ordering is what it costs.**
[ADR-10](adr/0010-data-artefacts-and-weight-ceiling.md) ships both as a plain ZIP with
`ZIP_DEFLATED` members (§3.2) rather than the `.tar.zst` a stdlib-only install has no decoder for.
The re-packaging is free while it lands **before** the first publication — `omniweave-golden` is
built at [roadmap](16-roadmap.md) W10.8 and `omniweave-index` at the `V20-6` line — because the
packager is then written once and the whole cost is roughly 15% on a one-time ~240 MB download.
Landing it after costs both digests, and a digest change is by the charter's own rule a permanent
failure that never triggers a fetch, so every installed copy would have to be told to re-fetch by
hand. That asymmetry, and not the download delta, is why the container carries a hard deadline.

**28 PyPI files, zero platform wheels, one runner.** That is the whole point of the
`py3-none-any` decision: no `cibuildwheel`, no manylinux images, no macOS arm64/x86_64 split, no
Windows compiler, and a release matrix of one. The `video` Toolchain ships no bundle because its card
declares `implemented = false` (§1.6), and the Node runtime is not ours to publish — §3.2's
`[[node]]` rows point at nodejs.org and carry the digests transcribed from its own `SHASUMS256.txt`. *(Build note, D874: `tools/check_build.py` asserts the `build` job's two artefact properties on any machine. **The repository holds zero publishing secrets.** PyPI is OIDC Trusted Publishing, cosign is keyless

what makes `step-security/harden-runner`'s egress audit a meaningful control rather than a formality:
the only thing a compromised step could exfiltrate is the run's own short-lived identity token.

> **Extends the charter.** The container image, the first-party manifest as a signed asset, and the
> standalone-installer *absence* are new decisions. The charter's CI inventory has a `parity` job

### 7.2 The first-party release manifest

[The driver system](04-driver-system.md) §4.2 computes a driver's trust as `first_party` when its
distribution name is in **the release manifest's first-party list** and its `dist_sha256` matches
that manifest. The charter names no home for that manifest. It is `first_party.toml`, generated
package data inside `omniweave-core`, published alongside the release as a signed JSON asset, and
its construction has one genuine ordering problem worth solving in the open.

```toml
# omniweave_core/drivers/first_party.toml — GENERATED by tools/gen_first_party.py. 13 rows.
schema = 1
release = "0.4.2"

[dist."omniweave-ports"]
version = "1.0.0"
dist_sha256 = "sha256:6f1c…"

[dist."omniweave-pdf"]
version = "0.4.2"
dist_sha256 = "sha256:9ab4…"
```

The problem: a manifest that hashes the wheels cannot live inside one of the wheels it hashes. The
resolution is a two-pass build (§6.6 step 2) plus one documented exclusion:

- Pass 1 builds all 28 files. `gen_first_party.py` reads the 26 non-core files and writes thirteen
  rows — every first-party distribution **except `omniweave-core` itself**.
- Pass 2 rebuilds only `omniweave-core`, whose wheel now contains the manifest. The other 26 files are
  byte-identical to pass 1, which the reproducibility assertion proves rather than assumes.
- **`omniweave-core` has no row, and that is the correct answer, not a gap.** Core is the verifier: it
  is the module computing the trust tier, so a row asserting core's own hash would be a witness
  testifying to itself. Core's integrity is covered by Release provenance — the GitHub build
  attestation and the SLSA bundle — which is a claim by the build system rather than by core.
- A distribution installed from the workspace (`uv sync`, `pip install -e`) has no wheel and therefore
  no `dist_sha256`. `first_party.toml` is generated *into* `src/` at build time and is `.gitignore`d,
  so a developer's checkout does not have one at all: `compute_trust` returns `unpinned` with a
  `Degradation(kind="pin")`, and §2.6's use-time read rule is what keeps that from being an
  `ImportError` on every `ow --version`. That is why §2.4's wheelhouse installs matter beyond weight
  measurement — the `conform` job runs against installed wheels precisely so trust computation is
  exercised on the shipped shape.

The published `first-party-<RELEASE>.json` asset is the same content in JSON, `cosign sign-blob`ed, so
an auditor can compare the in-wheel copy against a signed one without trusting the wheel that carries
it. The prefix `omniweave-` is reserved by the terminology lock and **not** by PyPI, which is exactly
why name-matching alone was never sufficient, why the hash is load-bearing, and why step 0 of §7.6
registers all **nineteen** names — the fourteen distributions plus §1.2's five attachment
distributions — before the first release rather than after it. *(Build note, D895: `tools/gen_first_party.py --dist dist` writes the manifest, one row per non-core wheel with `dist_sha256` = D894's RECORD digest, `vendored` from G12's `tools/vendor.toml` (`pinned_by`), and `release` = core's version; a missing, extra or duplicate wheel writes nothing. `ci.yml`'s step 2 runs it, removes core's pass-one files, rebuilds core, re-checks with `--check` and asserts core's rebuilt wheel carries `first_party.toml`; the manifest stays in `src/` for step 3, so its one 28-file diff compares 26 against pass one and core's two against step 2. Hatchling includes the gitignored manifest in both core artefacts, which was checked rather than assumed. Measured locally: 13 rows, `omniweave-office` vendored, 28 identical sha256s across the passes.)*

### 7.3 Signing and provenance

local-deep-research is the template, and the specific choices below are its recorded scars rather
than a generic checklist.

```yaml
# .github/workflows/release.yml — the shape, not the whole file
permissions: {}                       # minimal at the top level

jobs:
  ci:
    uses: ./.github/workflows/ci.yml  # THE RELEASE GATE IS CI. One definition.

  build:
    needs: [ci]
    permissions: { contents: read }
    outputs:
      hashes: ${{ steps.hash.outputs.hashes }}   # base64 sha256 of all 28 files
    steps:
      - uses: step-security/harden-runner@<40-hex>   # egress-policy: audit
      - uses: actions/checkout@<40-hex>              # persist-credentials: false, fetch-depth: 0
      - run: |
          SOURCE_DATE_EPOCH=$(git show -s --format=%ct HEAD) uv build --all-packages
          python tools/gen_first_party.py --dist dist/ --release "$RELEASE"
          rm dist/omniweave_core-* dist/omniweave-core-*
          SOURCE_DATE_EPOCH=$(git show -s --format=%ct HEAD) uv build --package omniweave-core
      - id: hash
        run: echo "hashes=$(sha256sum dist/* | base64 -w0)" >> "$GITHUB_OUTPUT"
      - uses: actions/upload-artifact@<40-hex>
        with: { name: dist, path: dist/, retention-days: 7 }   # §7.4. NEVER 1.

  provenance:
    needs: [build]
    permissions: { actions: read, id-token: write, contents: write }
    uses: slsa-framework/slsa-github-generator/.github/workflows/generator_generic_slsa3.yml@<40-hex>
    with:
      base64-subjects: ${{ needs.build.outputs.hashes }}
      provenance-name: provenance.intoto.jsonl
      upload-assets: false

  sbom-sign:
    needs: [build]
    permissions: { contents: read, id-token: write }
    steps:
      - uses: sigstore/cosign-installer@<40-hex>
        with: { cosign-release: 'v2.6.3' }
      - run: |
          cosign sign-blob --yes --bundle sbom-spdx.json.bundle sbom-spdx.json
          cosign verify-blob --bundle sbom-spdx.json.bundle \
            --certificate-identity-regexp '^https://github\.com/omniweave/omniweave/' \
            --certificate-oidc-issuer https://token.actions.githubusercontent.com \
            sbom-spdx.json

  publish:
    needs: [build, provenance, sbom-sign]
    environment: release                 # THE APPROVAL PAUSE, and it cannot move github.sha
    permissions: { id-token: write }     # PyPI Trusted Publishing, OIDC. No API token.
    steps:
      - uses: actions/attest-build-provenance@<40-hex>
        with: { subject-path: 'dist/*' }
      - uses: pypa/gh-action-pypi-publish@<40-hex>   # step 1: omniweave-ports, if it moved
      - uses: pypa/gh-action-pypi-publish@<40-hex>   # step 2: omniweave-core
      - uses: pypa/gh-action-pypi-publish@<40-hex>   # step 3: the eleven siblings
      - uses: pypa/gh-action-pypi-publish@<40-hex>   # step 4: omniweave
```

Nine rules, each with the defect it prevents:

1. **`cosign` is pinned to `v2.6.3`, not to the installer's default.** local-deep-research's comment
   is precise about why (`docker-publish.yml:100-106`): installer v4.1.2 ships cosign v3 by default,
   and v3's `new-bundle-format` changes the signature/attestation on-wire format so that a v3 producer
   and a v2 consumer cannot interoperate — *"Mismatched versions across sign/verify work today but
   new-bundle-format (cosign v3 default) would only produce/consume on v3."* The version that signs
   and the version in `docs/verify.md`'s recipe move together, in one commit, and both live in §6.7's
   table.
2. **Every third-party action is pinned by full 40-hex commit SHA with the version in a trailing
   comment.** A tag is mutable; `zizmor` lints the workflow files for unpinned uses on every PR
   (`gates.workflow_tools_pinned`). local-deep-research runs `zizmor-security.yml` for exactly this,
   and it is the workflow people forget: the CI definition is itself an attack surface with write
   access to the release.
3. **The SBOM is signed *and verified in the same job*.** Their own comment names the reason:
   *"cosign signs above but never verifies, so a sigstore/cert-chain regression would silently break
   downstream verification — caught only when a user complains."* The round-trip proves the recipe a
   user will run still works.
4. **The SBOM generator is SHA-pinned and its output is sanity-checked before signing.** Trivy can
   emit a near-empty SBOM on a partial scan failure without a non-zero exit; signing that produces a
   fraudulent SBOM carrying a legitimate Sigstore certificate. local-deep-research's shipped floor is
   **80% of the previous stable release's component count, per format**, with a hard floor of 50 when
   no prior SBOM is fetchable and a cap of 2000 against runaway drift — SPDX and CycloneDX counts
   differ because of virtual and metadata-only entries, so each format gets its own floor from its own
   prior count (`release.yml:415-475`). omniweave keeps the 80% rule and the 2000 cap and replaces the
   hard floor of 50 with the install profile's **declared direct dependency count**, which is 2 for
   the `minimum` profile's core (itself plus `omniweave-ports`) and is the smallest honest number a
   fourteen-wheel release can produce. A floor of 50 on a two-dependency profile would either never
   fire or always fire, and neither is a check.
5. **The container image is built once and promoted by digest.** Retagging by digest keeps the
   cosign signature, the SBOM and the SLSA provenance transitively valid; rebuilding for a second tag
   produces a different digest and silently orphans all three. The per-arch SBOM rule comes with it:
   syft against a manifest-list digest scans only the host platform's layers
   (`anchore/syft#1708`), so each per-arch digest is attested with its own SBOM and no manifest-level
   SBOM is produced at all, because a manifest-level one would be amd64-only and would lie to every
   arm64 consumer running the published verify recipe.
6. **`release.yml`'s filename is asserted by a gate.** Trusted Publishing binds the OIDC subject to
   `workflow_ref`; a rename revokes publishing with no local symptom. The same gate asserts that no
   job calling `pypa/gh-action-pypi-publish` appears in a workflow invoked by `workflow_call`, since
   `workflow_ref` names the caller and the publisher would get `invalid-publisher`.
7. **`environment: release` gates exactly the jobs that declare it** — `publish` and the GHCR promote
   job — and nothing else. An environment is per-job, not per-run; every other job in `release.yml`
   runs unattended before the pause. Stating it the other way round would be the same category of
   error the drift bug came from: an approval that is believed to gate more than it does. The
   environment additionally sets **required reviewers** and **prevent self-review**, so the person who
   pushed the tag cannot approve their own publish; a one-person release is possible only by
   deliberately configuring one reviewer who is not the tagger.
8. **Every artefact the publish job consumes is uploaded with `retention-days: 7`, never the
   default.** §7.4 is why, and it is the scar with the largest blast radius in the mined collection.
9. **"Attestation" is not used for release signing in any omniweave prose or code.** The terminology
   lock defines **Attestation** as the sha256 over a canonical driver card written by `ow conform` —
   tamper-evidence for a card, explicitly *not* a signature. Release signing is a **Release
   provenance** bundle. Conflating the two would let a driver author's passing conformance run read as
   a publisher signature, which is exactly the misreading charter §6.11 refuses to imply.

**The publish job uploads in four ordered steps, and the order is a partial-failure design.** PyPI
filenames are immutable: a partially completed upload cannot be retried into the same version, only
yanked and superseded. Uploading dependency-first — `omniweave-ports` (if its Port major moved), then
`omniweave-core`, then the eleven siblings, then `omniweave` — means every reachable intermediate
state is *unresolvable* rather than *broken*. If the run dies after step 3, `pip install omniweave`
resolves to the previous release, because the umbrella that would have pointed at the new siblings
does not exist. If the order were reversed, `pip install omniweave==<new>` would resolve and then fail
at its dependencies, which is a much worse failure to be in for the hours before anyone notices.

### 7.4 The approval pause, and what has to survive it

The pause is the only unbounded interval in the release, and everything the publish job needs was
built before it. GitHub deletes a workflow artefact at `retention-days`, and it does so without regard
for a run that is still waiting on a human. local-deep-research shipped the exact failure and wrote it
down (`release.yml:498-511`): with `retention-days: 1`, the v1.9.0 artefact expired **24 h** after the
build while the approval arrived **~30 h** later, `create-release` failed with "Artifact not found",
and the release was unrecoverable in place *because the signed SBOM bytes named as subjects in the
SLSA provenance no longer existed*. A provenance statement whose subjects have been garbage-collected
cannot be satisfied by regenerating the subjects, because a regenerated SBOM has a different digest.

Four rules, and the fourth is the one that makes the other three affordable:

1. **Every pre-approval upload sets `retention-days: 7`.** That is `dist/` and the SBOM bundles.
2. **The binding constraint is not ours to set.** `slsa-github-generator`'s reusable workflow uploads
   `provenance.intoto.jsonl` with a hardcoded `retention-days: 5` and exposes no caller input —
   verified by local-deep-research at their pinned v2.1.0 commit. So the **effective approval window
   is 5 days**, not 7. `CONTRIBUTING.md` states the number, checklist step 14 repeats it, and the
   7-day setting on our own uploads exists only so that ours is never the artefact that expires first.
   If the generator later gains a retention input, both values move together in one commit.
3. **An expired window is not recoverable by approving late.** The run is dead; approving it produces
   a job that cannot download its inputs.
4. **The recovery is to re-run the whole release from the same tag, and that is safe *because the
   build is reproducible*.** `build.reproducible` (§6.6 step 3) asserts that two passes produce 28
   identical sha256s, so a re-run from the tag produces byte-identical wheels, therefore identical
   SLSA subjects, therefore a provenance statement over the same digests. Reproducibility is not a
   purity exercise here: it is what converts a blown approval window from "cut a new PATCH and yank
   nothing, because nothing published" into "press the button again". Every other property of a
   reproducible build in this document is downstream of that one.

The corollary is a rule about what may *not* go before the pause. Nothing in `release.yml` that
produces an artefact the publish job needs may depend on wall-clock time, a network resource that can
disappear, or a mutable upstream tag — because all three make a re-run after a five-day gap produce a
different byte. That is the same constraint `SOURCE_DATE_EPOCH` and the 40-hex action pins already
impose, arriving from a second direction.

### 7.5 What a consumer can verify, and what they cannot

`docs/verify.md` carries four recipes and one paragraph of honesty.

```bash
# 1. a wheel's build provenance (GitHub attestation)
gh attestation verify omniweave_core-0.4.2-py3-none-any.whl --repo omniweave/omniweave

# 2. the SLSA provenance for the whole release
slsa-verifier verify-artifact omniweave_core-0.4.2-py3-none-any.whl \
  --provenance-path provenance.intoto.jsonl \
  --source-uri github.com/omniweave/omniweave --source-tag v0.4.2

# 3. an SBOM, or the first-party manifest (same recipe, different blob)
cosign verify-blob --bundle sbom-spdx.json.bundle \
  --certificate-identity-regexp '^https://github\.com/omniweave/omniweave/' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com sbom-spdx.json

# 4. the in-wheel first-party manifest against the signed asset
python -c "import importlib.resources as r, sys; \
  sys.stdout.write(r.files('omniweave_core.drivers').joinpath('first_party.toml').read_text())" \
  | python tools/manifest_diff.py first-party-0.4.2.json -
```

Recipe 4 reads through `importlib.resources` rather than `__path__[0]` for the reason §2.6 gives: the
recipe has to work against whatever layout the consumer installed into, and a path-based read is the
one that fails on exactly the installs an auditor is most likely to be inspecting.

The honest paragraph: these prove **a first-party artefact was built from this repository at this
commit by this workflow**. They prove nothing about a *third-party driver*. A driver's `Attestation`
is a hash over its own card computed by its own kit run, so an author can run the kit on a clean
build and ship a different wheel with the same card. Only `dist_sha256` in `omniweave.lock` catches
that, and only for consumers who installed through an index ([the driver
system](04-driver-system.md) §5.5). The documentation says so rather than implying a signature.

Ordered, and each step names the thing that fails if it is skipped. Step 0 runs once, before the
first release, and never again.

### 7.7 When a release goes wrong

| situation | what to do | what not to do |
|---|---|---|
| the publish job died between two of the four upload steps | bump the PATCH and re-run the whole release; the partially published version stays and gets **yanked** with a reason naming the successor | never delete a PyPI file — the filename is permanently consumed and the version becomes unbuildable, so a deletion converts a recoverable state into an unrecoverable one |
| the approval window expired and the run's artefacts are gone | re-run the release from the same tag; the build is reproducible, so the digests and therefore the provenance are the same (§7.4) | never rebuild from a moved branch, and never re-cut the tag |
| a wheel is published and then found defective | yank the version, ship the PATCH, and add the defect's detection to the gate that missed it in the same PR as the fix | never re-upload; never rely on the yank alone, since an exact pin still resolves a yanked version |
| a signed SBOM is wrong (a Trivy partial scan that passed the 80% floor) | regenerate, re-sign, replace the asset, and tighten the floor | never re-tag the image or re-build the wheels — the digests are the subjects of a signed provenance statement |
| the container tag points at the wrong digest | re-promote the correct digest to the tag | never rebuild for the tag: a rebuild produces a new digest and orphans the signature, the SBOM and the provenance together |
| the Trusted Publisher binding is revoked (a `release.yml` rename that reached the default branch) | re-create the publisher entry on PyPI for the new `workflow_ref`, then release; the gate of §7.3 rule 6 is what makes this a PR-time failure instead | never add an API token as a fallback — a long-lived secret is the thing §7.1's "zero publishing secrets" buys |

The one state with no clean recovery is a publish interrupted *mid-upload of a single step*, which is
why `release.yml` carries no `concurrency: cancel-in-progress` (§6.3) and why the four steps are
dependency-ordered rather than parallel.

Four of those rule families are load-bearing rather than stylistic. `DTZ` bans a naive `datetime`,
which pairs with semgrep's ban on `datetime.now()` in library code. `T20` bans `print` — a library
that prints has no way to be quiet inside a hook with a 400 ms deadline. `S` is the bandit subset, and
`S101` is confined by `per-file-ignores` to the conformance kit and to test trees rather than ignored
globally, because `assert` is how the testkit expresses a property and nowhere else. `TID` does two
jobs: `ban-relative-imports` is what makes `tools/gate_layers.py`'s `ast` walk able to map every
import to a first-party root without resolving anything, and `banned-api` + `per-file-ignores` is how
a *scoped module ban* is expressed in the fast linter.

`TRY003` is ignored deliberately and it is the one ignore that is a design decision rather than a
concession: charter §6.4 requires that every message ends with the command that clears it, so long
messages inside a `raise` are the house style and a rule against them would fight the framework's own
error contract.

**`ruff` does not replace `semgrep`, and the split is sharper than "one linter, one job".** Ruff
can express a banned *import* scoped by path, which is what the block above does for the five
forbidden modules — cheap, and it moves five of the collection's rules off a 45 s semgrep run onto a
sub-second one. What ruff cannot express is a ban on a *call shape*, and every remaining rule is one
of those: `conn.commit()` or `BEGIN` on any receiver outside `omniweave_core/store/`,
`zipfile.ZipFile(..., 'w')` outside `out/opc.py`, `DriverHost.invoke()` called from anywhere but
`run/pipeline.py`, `revision="main"` as an argument value, `open(..., "w")` without
`newline="\n"` under `tools/`, `__file__` or `__path__` anywhere under `packages/*/src/` (§2.6), and
a bare `except` around a digest or a cache key. Those are the rules that keep the seam count at four,
and they need a pattern language over expressions.
`local-deep-research/.semgrep/rules/ldr-security.yaml` is the shape adopted: a rule file in the
repository, run in CI, one rule per recorded defect.

### 8.2 pyright, and where it may run

**`pyright` runs only in `gates`.** The PyPI `pyright` shim downloads a Node runtime into a cache on
first use unless `PYRIGHT_PYTHON_GLOBAL_NODE=1` finds a `node` on PATH. The `gates` job sets that
variable against the runner's Node; the `parity` container has no Node **by design** and therefore
installs `pytest` alone. A type checker that silently fetches a JavaScript runtime is not something to
run inside the job whose entire purpose is to prove the framework needs no JavaScript runtime — and
running it there would make the Node-free claim self-refuting rather than merely untested.

`.pre-commit-config.yaml` runs the four cheap gates locally — `ruff format`, `ruff check`, G5
(`check_versions.py`) and G4 (`gate_layers.py`, an `ast` walk that needs nothing installed) — and
nothing that needs a network, a corpus or a Node runtime. A pre-commit hook that takes 30 seconds is a
pre-commit hook that gets bypassed, and graphify's measurement of the opposite choice is the warning:
a hook that imported the package wholesale cost 10 s+ cold and ran up to four times per commit.

### 8.3 Commits

Conventional Commits, with the scope drawn from a closed list checked by a gate: `core`, `ports`,
`cli`, `sdk`, `office`, `pdf`, `vision`, `graph`, `llm`, `serve`, `pptx`, `docx`, `deck`, `video`,
`conform`, `toolchains`, `schema`, `tools`, `docs`, `eval`, `fixtures`, `ci`.

```text
feat(pdf): emit glyph runs so INV-10's `glyphs` branch can re-verify a span

pdfium exposes per-glyph rects through FPDFText_GetLooseCharBox; the driver now
emits an OriginSpan with os_kind = "glyphs" and os_extractor = "pdfium/6.0.1"

```

`Signed-off-by` is required — a DCO, not a CLA, checked by a gate. Four footers are recognised:
`Charter:` (the section a change implements or amends), `Invariant:` (the invariant it touches),
`Gate:` (a gate whose generated artefact moved), and `Bless:` (required in the **same commit** as any
change to `schema/expected/` or `eval/baselines/`, with a reason of at least 20 characters, mirrored
into `eval/BLESS.log`; past 20% of files a second reviewer is required, and `OMNIWEAVE_BLESS` must be
set in the environment — docling's `tests/test_data_gen_flag.py` adopted whole as
`test_bless_flag_is_off()`).

Merges are **squash-only**, one commit per PR, and branch protection requires a branch to be up to
date before merging. Neither is taste: §5.2 shows that those two settings together are the whole
defence against two branches allocating the same identifier in an append-only register, and they
cover `codes.toml`, `schema/migrations/`, `tools/gates.toml`, `tools/invariants.toml`,
`tools/wirekeys.toml` and `tools/events.toml` with one mechanism rather than six.

### 8.4 Pull requests

The PR template is short and its checklist is charter §8's twenty-two rejection criteria, verbatim,
because a reviewer may reject on any of them without further argument. Four required fields:

- **which invariant this change touches, or `none`** — and `none` on a diff that touches
  `omniweave_core/store/`, `route/eval.py`, `retrieve/verdict.py` or any `*Sink` is itself a review
  finding;
- **which gate proves it** — a behavioural change with no gate delta is either untested or the gate
  is missing;
- **for a new dependency: the resolved closure delta in MB, the SPDX identifier, and the reason a
  looser constraint will not do** (G7 requires a comment on any constraint tighter than `>=`);
- **for a deprecation: which of §4.4's three phases this PR performs**, since phases 1 and 2 must land
  in different releases and no tool can check that.

**Review load: one approval normally; two for the contract-bearing paths — and GitHub cannot express
that literally, so here is what it does express.** The paths are `codes.toml`, `tools/*.toml`,
`schema/migrations/`, `packages/omniweave-ports/`, `omniweave_core/contract.py`, any invariant's
enforcer, `.github/workflows/` and anything under `docs/adr/`. Each is a `CODEOWNERS` entry naming a
team; branch protection sets `required_approving_review_count = 1` **and** *Require review from Code
Owners*. A PR touching one of those paths therefore needs the generic approval **plus** an approval
from the owning team — two distinct people whenever the author is not themselves a code owner, and
exactly one when they are. That residual is real and is not argued away: the compensating control is
that every one of those paths is also append-only or generated and gated, so an unreviewed edit still
fails CI rather than merging quietly.

```text
# .github/CODEOWNERS
*                                                          @omniweave/maintainers
/codes.toml                                                @omniweave/contract
/tools/                                                    @omniweave/contract
/schema/migrations/                                        @omniweave/contract
/packages/omniweave-ports/                                 @omniweave/contract
/packages/omniweave-core/src/omniweave_core/contract.py    @omniweave/contract
/docs/adr/                                                 @omniweave/contract
```

A change that amends the charter is an ADR that names the section, quotes the old text and the new,
and records which ruling's ADR must be re-issued — and it may not land in the same PR as the code that
depends on it.

### 8.5 The dependency pin policy

Two mined repositories demonstrate opposite, defensible policies, and mixing them silently is the
failure. local-deep-research floors with CVE comments and no ceiling, optimised for patchability, and
its comments say what a floor *means* — *"1.12.0 is the reviewed floor: never resolve below it, and
re-check the parser contract and its tests before raising the ceiling."* graphrag pins near-exactly
(`graspologic-native>=1.2,<1.3`, `nltk~=3.9.0`, `litellm==1.97.0`) with a reason and an exit —
*"nltk 3.10 changes the perceptron POS tagger / tokenizer output, which shifts the deterministic
noun-phrase extraction counts and breaks the pinned NLP regression tests. Revisit deliberately with a
golden-data refresh."* olmocr does the same in its `gpu` extra (`transformers==4.57.3`,
`vllm==0.11.2`). Both are right for their role. The policy assigns each dependency a role:

| role | policy | rationale |
|---|---|---|
| anything reachable from untrusted input — XML/HTML/PDF parsers, archive readers, HTTP clients, TLS | **floor with a CVE comment, no ceiling**; a specific bad release is excluded with `!=`, never by raising the floor | a ceiling here is an unpatchable CVE, and raising a floor to skip one bad release also forbids the good releases below it — docling's `pypdfium2 (>=4.30.0,!=4.30.1,<6.0.0)` is the habit worth copying |
| anything whose output is a golden — tokenisers, clustering, embedders | **exact pin permitted**, and it must carry a named owner, a refresh procedure, a review date and an issue link | reproducibility is a real requirement; amnesia is not |
| model weights | **exact commit SHA + file hashes**; `revision="main"` is a lint error (G8) | docling's own `revision` defaults to `"main"` across six RT-DETR layout models, and three of its VLM presets set `trust_remote_code=True` |
| vendored binaries and source | **sha256 recorded + a parity test between copies + an arch assertion + a NOTICE row** (G12) | Unlimited-OCR's documented install step one is a 12.4 MB unsigned prebuilt wheel committed to git, with no hash, no signature and no index. codegraph has the hash and the parity test and not the notices; hyperframes has the arch assertion and neither of the others. All four together is the rule |
| a CI-only executable | **not a dependency at all** — a SHA-pinned action or `uvx <name>==<exact>` | §6.7; it must never enter the workspace environment, because the dev group is fixed at ten packages by [system architecture](02-architecture.md) §3.3 |

`firecrawl-anydoc == 0.2.4` is an exact pin under the second role and carries its justification in
the `pyproject.toml` comment: single-vendor, three months old, an unaudited transitive
`pdf-inspector = "1.14.2"`, MIT source vendored at `vendor/anydoc/`, and a written fork trigger.

### 8.6 How the architecture document is kept from drifting: G27(d)

> **Extends the charter.** G27 currently has three clauses — fenced blocks parse under the parser
> their fence names, migrations apply in numeric order to an empty file, and the terminology lock
> holds in both directions. Clause **(d)** is added here, adopting graphify's mechanism:
> `tests/test_architecture_doc.py` parses the table rather than restating it, imports every symbol it
> names, and its docstring records exactly what drift cost — *"It had drifted to document six
> functions that do not exist … Anyone following it wrote code that raised, or — worse for
> `extract()` — code that ran and silently produced non-canonical ids."* No new gate number is
> created; G27 is already the gate that machine-checks the documents.

`tools/gate_docs.py` walks `docs/ARCHITECTURE.md` and `docs/plan/*.md` and asserts five things:

| clause | what it checks | failure looks like |
|---|---|---|
| **d0 the walk found something** | the symbol regex matched at least the count in `tools/gates.toml`, and `omniweave_core`, `omniweave` and `omniweave_ports` are all among the roots found | `G27d FAIL parser matched 3 symbols, floor is 520 — the regex is broken and every check below is vacuous` |
| **d1 symbols** | every dotted name matching `^omniweave(_[a-z]+)*(\.[a-z_]+)*(\.[A-Za-z_]\w*)?$` in a document either imports, or is a declared-and-not-yet-built row in `docs/plan/16-roadmap.md`'s milestone table. A bare root with no dotted tail is not a symbol (d0 owns the roots) and is not counted by d4; a `from <root> import (A, B)` line inside a fenced `python` block expands to `root.A` and `root.B` and each is checked | `G27d FAIL docs/ARCHITECTURE.md:212 omniweave_core.retrieve.rerank — no such attribute (did you mean `fuse`?)` |
| **d2 registers** | every `tools/*.toml` filename, `ow <group> <verb>`, config key, `OMNIWEAVE_*` env var, `OW-*` code, `G<n>`, `[[job_assertion]]` name and identifier in the nine invariant families — `INV-<n>`, `M-INV-<n>`, `DR<n>`, `RT<n>`, `ST<n>`, `I<n>`, `GR<n>`, `OUT<n>`, `SV<n>` — named in a document exists in its register; and every spelled-out distribution count equals `len(glob("packages/*/pyproject.toml"))` | `G27d FAIL docs/plan/07-store-and-retrieval.md:118 ow store rebalance — not in the ACTIONS registry (nearest: ow store reshard)` |
| **d3 links** | every relative markdown link resolves to a file, and every `§n.n` cross-reference names a heading that exists in the target | a moved section, or the `_plan/` → `docs/plan/` move breaking a link |
| **d4 count** | the number of symbols checked, emitted as the Counter `docs_symbols_checked` with `ratchet` gating | a document that stops naming things to make the gate quiet |

Clause d0 is the one most adopters drop, and graphify's own test is why it is here: a regex that
silently matches nothing turns every parametrized assertion below it into a pass. The floor lives in
`tools/gates.toml` beside G27's row, so raising it is a reviewable act and lowering it is visible. It
is **520** at release 1, against the **620** symbol occurrences the nineteen plan documents match
under d1 — 588 dotted names plus 32 names expanded out of `from <root> import (…)` lines — plus
whatever `ARCHITECTURE.md` contributes. Set below the real count so an ordinary document edit does
not fail the gate, and far enough above zero that a regex matching only the three roots cannot
satisfy it. The number moved from 400 to 520 when d1's module group became a `*`: a floor inherited
from a narrower match set is a floor that no longer measures anything.

**Why d1's module group is a `*` and not a `+`.** A `+` requires at least one all-lowercase dotted
segment after the root, so a **two-segment reference to a top-level re-export never matched** and was
silently unchecked — and that is the most-cited and most-rename-exposed shape in the whole plan:
`omniweave_ports.CostClass` ([interfaces](10-interfaces.md) §2.1) and
`omniweave_ports.ArtifactKind` ([the driver system](04-driver-system.md) §2.3), and all twelve
names [the API sketch](18-api-sketch.md) §5.2's reference driver imports in one
`from omniweave_ports import (…)`. d0 does not catch the omission, because d0 only asserts that the
three roots appear at all; a regex can match five hundred `omniweave_core.retrieve.*` names, satisfy
the floor, and still check none of the type surface a third-party driver actually writes against. The
`*` costs one disambiguation, which the two clauses in d1's row buy: a bare root is **not** a symbol
(there is nothing to import-check beyond what d0 already asserts, and 1,619 bare-root occurrences in
`docs_symbols_checked` would drown d4's ratchet in prose noise), and a `from <root> import (A, B, C)`
line in a fenced `python` block is expanded to `root.A`, `root.B`, `root.C` before the check, so an
import list is verified name by name rather than discarded as one bare root. *(Build note, D986: `docs/ARCHITECTURE.md` is written and clause (d) runs in part. `packages/omniweave-core/tests/unit/test_architecture_doc.py` is graphify's mechanism adopted literally -- it PARSES the document rather than restating it, so a table row added later is checked without editing the test: d0's floor (25 symbols over this one document, not the 520 the nineteen plus this one would match), d1 by import-then-getattr over the longest importable prefix, and d2's checkable shapes -- every `ow <group> <verb>` against `ACTIONS`, every `G<n>` against tools/gates.toml, every register path against the filesystem, and the distribution table against `glob("packages/*/pyproject.toml")` in both directions. Planting `omniweave_core.retrieve.rerank` in the document fails the parametrised case named for it. `tools/gate_docs.py` is still unwritten and the reason is not the script: this section's walk includes `docs/plan/*.md`, section 1.5's move of the nineteen documents out of the gitignored `_plan/` has not happened, so the 520 floor cannot be met by anything in the tree and a gate asserting it would fail on an input that does not exist. G27's row and ci.yml's step now say that rather than naming a missing harness. The move is a ruling the repository owner owes, because committing the design record publishes it.)*

Clause d1's escape hatch is deliberate and narrow: a plan document legitimately names symbols that do
not exist yet. The escape is a **row in the roadmap's milestone table**
([build order and milestones](16-roadmap.md)), not a comment or an allowlist file, so an unbuilt
symbol is always also a scheduled one. Clause d4 is why the escape cannot be abused:
`docs_symbols_checked` ratchets, so removing a symbol from a document to silence d1 lowers a number a
gate watches. Counters catch what a clock cannot — a silent re-render, a re-billed free operator, a
document that quietly stopped describing the code.

Clause d2's distribution-count check is the one that keeps §1.10 honest. "Fourteen" appears in this
document, in the charter and in `ARCHITECTURE.md`; a PR adding a fifteenth distribution and forgetting
to update the prose fails on all three files at once, with the count it found and the count it
expected in the message. The registers d2 resolves against are the ones §1.7 defines, and two of them
exist only because of this clause: `tools/gates.toml` for the `G<n>` and `[[job_assertion]]` families,
and `tools/invariants.toml` for the **nine** invariant prefixes. Both are append-only against the
previous tag, so an identifier a shipped document names can never stop existing.

**`M-INV-<n>` is the ninth family and its rows are not optional.** [The document
model](03-document-model.md) defines five document-model-local invariants — `M-INV-1` and `M-INV-2`
in its §12.3, `M-INV-3` in its §16.5, `M-INV-4` in its §4.1 and `M-INV-5` in its §5 — and one of
them, `M-INV-3`, is the projection law on which that document's whole §16 rests. They are
subordinate to the framework `INV-*` series exactly as `DR`, `RT`, `ST`, `I`, `GR`, `OUT` and `SV`
are, so they get register rows on the same terms: five `[[inv]]` rows in `tools/invariants.toml`, one
`[[family]]` row naming [the document model](03-document-model.md) as the document that assigns the
numbers, and the append-only property that follows both. Eight families would have left the five
model invariants inside a gated document with no row and no existence check — which is the exact
drift d2 exists to catch, and the projection law is not a place to discover it late. The scan that
resolves them is **longest-match with a left boundary that rejects both word characters and `-`** —
`(?<![\w-])(?:M-INV|INV)-\d+`, and the same shape for the seven bare-prefix families — because
`INV-3` is a proper substring of `M-INV-3` and the two name different statements under different
numbering. A scan without that boundary resolves `M-INV-3` against the framework register, finds a
row, and reports a pass for an identifier it never looked up.

### 8.7 The contribution path

| you want to | you do | what you never touch |
|---|---|---|
| fix a bug | fork, branch, PR against `master`; one approval; the nineteen-job CI must be green | `tools/*.toml`, `codes.toml` |
| add an error code | append a row to `codes.toml` with both spellings, a meaning and **the exact command that clears it**; two approvals; rebase if the base moved (§5.2) | an existing row's number, ever (G13) |
| add a driver | `ow drivers scaffold`, then publish it as **your own distribution in your own repository**; run `ow conform` and ship the badge | this repository — third-party drivers are out of tree on purpose |
| add an install host | one file implementing `AgentTarget` plus one registry row; `print_config` must not touch the filesystem | the other hosts' files |
| add a compile target | a new `omniweave-target-*` distribution with `constructs.toml`, a `RulePack`, `lower()` and `read_back()`; its `layers.toml` row is `["omniweave_core", "omniweave_ports"]` and G4 derives it from your entry points | `omniweave_core.out` — the framework validates you, and there is no `validate()` to override |
| add a distribution | the ten sites of §1.10, in that order, in one PR | the count fourteen anywhere it is spelled without also changing the tree |
| add a migration | a new highest number; rebase and renumber if the base moved; declare `cost_class`, `resumable` and `unbackfilled_means` | any migration the previous tag contains, ever (§5.2) |
| change an invariant | an ADR naming the section, the old text and the new, in its own PR, with two approvals, before the code | the code, in that PR |
| add a gate | an ADR — not because a count is quoted anywhere, but because a `G<n>` is a numbered promise a document may cite — then a `tools/gate_*.py`, a row in `tools/gates.toml` with an owner and a review date, a row in §6.4's table, and a fixture that fails without it | another gate's number, ever |
| add a job assertion | a `[[job_assertion]]` row plus the step that asserts it — no ADR, because it creates no new promise a document can name numerically | the G-series |

The one thing the path deliberately does not offer is a plugin registry with automatic listing.
awesome-skills' governance model is the one adopted, and it is adopted whole: a published
`SECURITY.md` threat model, a written list of **hard rejects**, and human review as the entry
condition, staged as *"Stage 1 — Mechanical gate (CI: PR scope, checklist, frontmatter/description
limits, telemetry flags, referenced Actors, referenced paths, tracking parameters, schema drift);
Stage 2 — Content rubric (4 questions, 'a fail is a specific, quotable finding'); Stage 3 — Live smoke
test"* (`awesome-skills/REVIEWING.md:11-13`). Their own threat model states the thing a registry
maintainer most wants to forget: a validator supplied by the submission validates nothing. A registry
that lists on submission is a distribution channel for whatever was submitted.

## 9. Licensing and the segregation mechanism

### 9.1 The project's own licence

**Apache-2.0**, and the attribution files travel inside every artefact:

```toml
# every packages/*/pyproject.toml
license = "Apache-2.0"
license-files = ["LICENSE", "NOTICE", "THIRD_PARTY.md", "LICENSES/*"]
```

**There are sixteen copies of those files and not one, and the reason is a PEP 639 rule rather than a
preference.** `license-files` globs are resolved relative to the *project* directory — the directory
holding the `pyproject.toml` — and a pattern that escapes it with `..` is rejected by the
specification. `packages/omniweave-core/` therefore cannot reference the repository root's `LICENSE`,
and a build that tried would either fail or, worse under a pre-1.27 hatchling, produce a wheel with no
`License-File` entries at all (§1.3). So `tools/gen_notice.py` writes the four attribution artefacts
into each of the fifteen `packages/<dist>/` directories plus the repository root, all committed, all
`--check` gated inside G3. Sixteen copies of the Apache-2.0 text is about 177 KB in the repository and
is the price of the licence actually shipping. *(Erratum, D999, a user ruling of 2026-10-27: the four counts in this document were fifteen and fourteen -- right when they were written, and one behind a tree that gained `omniweave-langchain`. `tools/gen_notice.py` takes the set from `glob("packages/*/pyproject.toml")` rather than from a number, so it always emitted sixteen; the numbers are amended to what it emits, and a test reads this sentence and compares it with the tree. The **distribution** count of §1.2 and §7.2 is a second, separate erratum and is deliberately not touched here.)*

The duplication buys something beyond compliance. `THIRD_PARTY.md` is **per distribution and therefore
different in each one**: `omniweave-pdf`'s lists pdfium's BSD-3-Clause, `omniweave-target-pptx`'s lists
five packages, and `omniweave-core`'s lists nothing at all — which is the most useful attribution file
in the repository, because it is a machine-generated proof of INV-2 that a compliance reviewer can
read without running a resolver. No per-file licence headers: they are noise that drifts, and `NOTICE`
plus `THIRD_PARTY.md` carry the information a reviewer actually needs.

codegraph's lesson is why the glob includes `LICENSES/*` rather than stopping at `NOTICE` —
*"generate `THIRD-PARTY-NOTICES.md` in CI from the dependency graph and from an explicit vendored
manifest, fail the build if any vendored binary lacks an entry, and ship the file in every artefact
(npm tarball, wheel, container image, Lambda zip)"* — and it is why §7.1's container image carries the
same four files at `/usr/share/doc/omniweave/`. A notice that exists only in the git repository is a
notice that does not travel with the distribution, which is the only place the licences require it.

Contributions are under a **DCO** (`Signed-off-by`), not a CLA — checked by a gate, because an
unenforced DCO is a comment.

Apache-2.0 rather than MIT for one reason: the patent grant. omniweave compiles video and audio and
touches codec-adjacent territory (`[targets.video] codec = "vp9"`, with h264 an operator-owned opt-in
and never a fallback), and an explicit patent grant plus the §3 termination clause is worth more than
the shorter licence text. The precedent for relicensing being real is in the collection: graphify
relicensed from MIT to Apache-2.0 in 2026 (`graphify/NOTICE`), which is why `vendor/graphify-ids/` and
`vendor/graphify-security/` are pinned to a SHA with the NOTICE captured at that SHA rather than
tracking the repository. omniparse is the other end of the same axis and the reason a licence claim is
checked rather than read: its `LICENSE` is GPL-3.0 while its `pyproject.toml` declares
`license = "Apache"`, and the two have never been reconciled.

### 9.2 The segregation mechanism, in seven layers

The requirement is that a restrictively-licensed driver cannot reach a default install, and cannot
run even when installed. No single layer does that; seven do, and each one fails independently.

| # | layer | keeps out | mechanism |
|---|---|---|---|
| 1 | **it is not in the repository** | Datalab weights, HunyuanOCR, jcodemunch, omniparse | there is no vendored copy, no extra, no tombstone-adjacent stub with a fetch path. The single biggest licensing trap in the collection — marker/surya/lift's byte-identical modified OpenRAIL-M `MODEL_LICENSE`, whose Attachment A clause 2 has three independent gates and whose clause 8 reaches the *output* — is avoided by not shipping the weights at all |
| 2 | **`tools/licences.toml`, checked three ways (G3)** | AGPL and GPL arriving transitively | the **resolved graph**, the **import graph** and the **unpacked artefacts**. All three are needed: `cairosvg` (LGPL-3.0) is imported by `ppt-master/.../svg_to_pptx/pptx_package/media.py` and `visual_review.py` and is absent from its `requirements.txt`, so it is invisible to any manifest-based SBOM — which is the proof that manifest scanning alone is insufficient |
| 3 | **an extra may name only an `omniweave-*` sibling (G14)** | a third party arriving through `omniweave[...]` | there is no syntax by which an extra can pull a non-sibling, so an extra can neither add a licence nor add an egress path |
| 4 | **`[licence] allow_tiers = ["open"]` is the shipped default** | a `restricted` driver that *is* installed | `compute_tier()` derives the tier in core from the card's `[licence.*]` facts; a driver above the allowed tier is refused at `resolve()` with a named `Rejection`, not skipped |
| 5 | **`omniweave.acks.toml`, void on `licence_sha256` change** | a stale acknowledgement | a per-driver acknowledgement bound to the hash of the licence text. Upstream edits the licence, the ack goes stale, and the driver stops being auto-selected with `LICENCE_ACK_STALE` |
| 6 | **framework tombstones** | a known-forbidden `DriverId` being re-created by anyone | six shipped cards at release 1, each carrying the reason, the jurisdiction facts and a `[licence.weights].licence_sha256`, so installing the real thing produces a named refusal rather than a resolution |
| 7 | **`restriction_bits` propagates and blocks the OUT direction (INV-16)** | restricted content leaking into a compiled artefact | stamped by the runner onto every block, segment, entity, mention, edge, claim, asset and artefact; `NOT NULL` columns plus partial indexes on every carrier; the `compile` host **refuses**, naming the offending cites and asset ids |

Layers 4 through 7 are [the driver system](04-driver-system.md) §7's mechanisms; layers 1 through 3
are this document's, and layer 2 is the only one that runs at build time rather than at resolve time.
That split is deliberate: a build-time check can only see what the resolver installed, and a
resolve-time check can only see what a card declares, so a driver that is licence-clean to install and
restricted to run is caught by 4–7 and a dependency that is licence-clean on paper and copyleft in
fact is caught by 2.

Every entry is a *transitive or undeclared* dependency of an MIT- or Apache-licensed package, which
is why direct manifest scanning is not the mechanism.

| package | licence | where it hides | consequence |

Dev-only in `surya/pyproject.toml:48` and bench-only in `anydoc/bench/requirements.txt:2`, both of which are fine and worth distinguishing | AGPL §13's network clause on a served product |

This is why `[targets.video] ffmpeg = "system"` and **never** `"bundled"` |

Model weights are treated as licensed artefacts with their own SPDX entry in the SBOM, and
`tools/licences.toml` maintains an **allowlist with a justification per entry**, reviewed once per
release as checklist step 5. An allowlist without justifications becomes a list of things nobody
remembers approving.

### 9.4 Two things a reader should be able to check

Because the aggregate claim "omniweave is licence-clean" is not falsifiable and these two are:

1. **`pip download omniweave[recommended] && pip-licenses --allow-only=<the tools/licences.toml
   allowlist>` exits zero**, and it is the same allowlist G3 reads. local-deep-research's
   `license-check` job is the template, including the specific traps worth copying: use
   `--allow-only` (a denylist misses `UNKNOWN`), use version-specific CC-BY entries so `CC-BY-NC` and
   `CC-BY-SA` cannot match, spell "Mozilla Public License 2.0" so MPL-1.0/1.1 cannot match, and
   record every `--ignore-packages` exception with the metadata bug or tri-licensing that justifies it.
   `pip-licenses` runs through `uvx` at an exact version (§6.7) and never enters the dev group.
2. **`ow drivers check --posture` prints, per enabled driver: the computed tier, the
   `licence_sha256`, the acknowledgement state, the jurisdiction facts checked against
   `[licence] jurisdiction`, and the `restriction_bits` it stamps** — the report specified in
   [the driver system](04-driver-system.md) §7.4, which `ow doctor` runs as one of its checks and
   fails on. A licence posture nobody can print is a licence posture nobody audits, and one nobody
   has to remember to look at is the only kind that gets looked at.

### 9.5 Security disclosure

`SECURITY.md` carries a disclosure address, a **90-day** coordinated-disclosure window and a stated
response SLA, because exactly one repository in the twenty-two mined had one at all
(local-deep-research, `SECURITY.md:37-45`, with 30/45/60/90-day windows by severity, a 48-hour
acknowledgement and a one-week assessment; open-slide has a policy file but no SLA). It also carries
the residual risks the charter refuses to argue away, in the same words: `subproc` is not a security
boundary without OS support, so on macOS and Windows `needs_network = false` degrades to a
process-level guard a determined malicious driver in that process can bypass; **a compromised
publisher's driver with read access to `source_ro` can exfiltrate a corpus**; and
`$OMNIWEAVE_HOME/toolchains/` is a user-writable directory holding executable code. A security policy
that omits its own residual risk is marketing. [Security, privacy and licensing](14-security.md) owns
the threat model those risks belong to; this section owns only the file, its SLA and the fact that the
release checklist has no step that can waive it.

**OQ-2 — the weight-ceiling column needs a charter erratum — CLOSED** by
[ADR-10](adr/0010-data-artefacts-and-weight-ceiling.md): the column reads **marginal**, `aggregate_mb`

**OQ-3 — does `omniweave` keep its `omniweave-office` edge? (charter F33)** It puts a third-party
compiled `abi3` wheel on the default install path and it is the only first-party edge in the graph not
forced by a protocol. **What closes it:** counting platform-support issues attributable to
`firecrawl-anydoc` over the first two releases. **Pre-committed fallback:** move office behind
`omniweave[office]` and print the remedy in the "no driver for .docx" error. Only the dependency row
changes — and §2.3's laptop-minimum profile drops from 44 MB to 29 MB, which makes the fallback an
improvement on one axis rather than a pure loss.

**OQ-4 — how much runner-class variance do G10 and G26 actually see?** The hard assertions are on
deterministic module counts, so a runner-image change cannot produce a false failure there; the
wall-clock band is 25% against a per-OS baseline, best-of-five, and that number is inherited rather
than measured. **What closes it:** 100 consecutive `test` runs on an unchanged commit, reporting the
coefficient of variation of each of the six cold-start measurements per OS. **Fallback:** widen the
band to 40% for the two macOS/Windows cell groups and keep 25% on ubuntu, rather than widening all
nine — a gate that is loose everywhere catches nothing anywhere.

**OQ-5 — should `omniweave-conform` be one distribution or two?** It carries the driver testkit (which
a third-party author dev-depends on), the twelve conformance suites, the eval harness, the reducers,
the Cassette codec, the calibrator, the scoreboard generator **and** the reference target
`compile.text.owtext` — which is why its `layers.toml` row is the `compile` one. A driver author who
wants ~120 property tests currently installs the eval harness too, inside its charter-declared 5 MB
ceiling. **What closes it:** the measured import weight and install size of the testkit alone once the
harness exists. **Fallback:** keep one distribution. Two would put a version-skew seam between the kit
that writes a card's `[cost.measured]` block and the harness that reads it, which is worse than the
few megabytes at stake — and, per §1.10, a fifteenth distribution costs ten declaration sites.

**OQ-6 — G19's PR-time budget is a guess.** 300 documents in 40 scripted mutations, diffing `.owdoc`
exports, is budgeted at <= 8 min on the strength of the fixture size (Tier A is <= 64 MB total) and
nothing else. **What closes it:** running it. **Fallback:** if it exceeds 12 min, G19 moves to nightly
and the PR path keeps a deterministic 60-document/8-mutation subset with the mutation seed derived
from `blake2b(commit_sha)` — which weakens the gate on the PR path and is a trade to make with a
number in hand, not before. The `ci.job_seconds.incremental` Counter (§6.6) is what produces the
number without anyone remembering to look. *(Build note, D908: closed with a number. Through the product -- both stores built by real `ow add` children since D905 made an edit its document's next generation -- the 300/40 run measured ~24 min, so a user ruling of 2026-10-21 took the fallback: `ci.yml` gains a `schedule:` trigger, the `incremental` job runs `tools/gate_incremental.py --through-add` (300/40) on it and `--through-add --subset <commit>` (60/8, `blake2b(commit_sha)`, ~2 min) on a PR. `tools/incremental_add.py` is the builder; the stub build stays as the unflagged mode.)*

**OQ-7 — the single-`release.yml` design has one external dependency this document cannot control.**
Trusted Publishing's OIDC subject binds to `workflow_ref`, and the checklist, the gate and the naming
rule all rest on that binding staying filename-shaped. If PyPI ever supported reusable publish
workflows, §7.3 rule 6's second assertion would become wrong rather than merely unnecessary.
**What closes it:** nothing we can run. The mitigation is that a publish failure is loud and terminal,
never partial within a step, and step 16 of the checklist installs the published wheel from a clean
machine before the release is announced.

**OQ-8 — the CI cache budget arithmetic rests on one estimated number.** §6.6 computes 4.0 GB per
lockfile generation against GitHub's 10 GB LRU ceiling from an estimated ~400 MB per `uv` cache key.
If the real figure is 700 MB, two live generations already exceed the ceiling and every "warm" number
in §6.2 and §6.6 is wrong. **What closes it:** `gh cache list --limit 200 --json key,sizeInBytes`
after one week of real PR traffic. **Fallback:** drop the per-Python dimension from the `uv` key (one
key per OS, resolved for the lowest supported Python and shared) which trades a partial-hit penalty on
the 3.12 and 3.13 cells for a third of the storage.

**OQ-9 — `SCHEMA` has three homes and two of them are code — CLOSED** by
[ADR-9](adr/0009-schema-single-home.md): the code home is `omniweave_core.contract`, holding `SCHEMA`
and `SCHEMA_MINOR`; the disk home is `index_state.schema`; `meta` never gains a `schema` key, and its
DDL never listed one; and charter erratum `E72` amends §2's version axes. §4.1 is the settled
statement's sole home. Two corrections to what this entry used to propose are worth keeping: the
`.owdoc` justification for a denormalised copy fails against [the document
model](03-document-model.md) §13.2's `manifest.json` key set, which carries no `SCHEMA`; and the
interim mitigation was unrunnable as written, because `index_state` is created by `0003_index.sql`
and not `0001_init.sql` (§5.1) — so `G27(b)` asserts the single `schema` row at the **end** of the
`0001` → `0005` run, and `ow store verify` checks an absence rather than comparing two copies.
**This entry is otherwise a pointer and carries no fact of its own.**

**OQ-10 — the G-series is closed at 27 by a core document — ANSWERED** by
[ADR-2](adr/0002-invariant-and-gate-registers.md), which took this entry's recommended closer rather
than its fallback. `V10-1` ([00-vision.md](00-vision.md):724) drops the literal 27: its `G` half now
reads "every `G` row in `tools/gates.toml` green", charter X32's "CI gates are `G1-G27` and nothing
else" and the T0 pyramid row are superseded (errata `E33`, `E34`), and new gates are ordinary
appends. `G28` and `G29` are the first two (§6.4). Adding a `G<n>` still requires an ADR, on §8.7's
numbered-promise argument rather than on a quoted count. The `build` job's reproducibility assertion
(§6.6 step 3) **stays** a `[[job_assertion]]`: it is cited by no document by number, which is the
line the two families now fall on. **This entry is a pointer and carries no fact of its own.**

**OQ-11 — the effective approval window is set by a third party's hardcoded constant.** §7.4's
five-day figure is `slsa-github-generator`'s internal `retention-days: 5` on the provenance artefact,
which exposes no caller input; our own uploads are seven days precisely so ours is never the binding
one. That number can change under us in a version bump, and the symptom would be a release that
becomes unrecoverable a day earlier than `CONTRIBUTING.md` says. **What closes it:** a check in the
release job that reads the generator's own workflow at the pinned SHA and asserts the constant is
still 5, failing the release if it moved — cheap, since the SHA is pinned and the file is in the
checkout of a public repository. **Fallback:** self-host the provenance step, which trades one
maintained dependency for the whole SLSA generator, and is not worth it below a measured recurrence.

**OQ-12 — which distribution implements `ow eval`, and therefore what may read the golden corpus? —
CLOSED** by [ADR-10](adr/0010-data-artefacts-and-weight-ceiling.md) decision 4: `omniweave-conform`
implements the `eval` Action group and **the registry does not move**. Every `eval` row stays in
`ACTIONS` in `omniweave` with its `inp`/`out` types, and the dispatcher lazily imports
`omniweave_conform`, refusing when it is absent in the same shape as the "no driver for `.pdf`"
refusal — because the seven agent-facing surfaces are generated from `ACTIONS` and byte-diff gated,
so an Action that registered itself from `omniweave-conform` would make `ow surface emit --check`
pass or fail by environment. §2.2's rule that `omniweave` must not depend on `omniweave-conform` is
intact. [Interfaces](10-interfaces.md) §2 is the answer's sole home. This no longer moves OQ-1's
ranking: exit (c) was complete for `omniweave-golden` and never for `omniweave-index`, which the
runtime reads before install. **This entry is a pointer and carries no fact of its own.**

## New terms

Proposed for the terminology lock. Each is a concept this document needed and could not name from §2.

| Term | Kind | Definition |
|---|---|---|
| Attachment distribution | concept | A separately versioned wheel whose whole purpose is to attach omniweave to a third party's type system — the five rows of §1.2's second table. Outside the fourteen, outside `first_party.toml`, outside the 250 MB aggregate gate and outside `RELEASE`, because each tracks its third party's minor series; §4.3's fan-out takes five of its ten sites. Distinct from a driver distribution, which implements a Port and is discovered through an entry point rather than imported by name from the other side. |
| Install profile | concept | One of the six named `pip`/`uv` invocations in §2.3 — laptop-minimum, laptop-working, CPU server, GPU server, browser (which installs nothing) and CI — each with its distribution set, its `tools/weights.toml` ceiling sum and its cold-start budget. A profile is a **tested install command**, not a documentation heading: the `build` job installs three of them into fresh environments from an offline wheelhouse and G2 measures them (§2.4). Spelled with the word *install* because the lock reserves bare `Profile` for the agent surface's listed-set. |
| Marginal weight | concept | A `tools/weights.toml` row: a distribution's own installed files plus the third-party closure it introduces, **excluding first-party siblings**, each of which is counted in its own row. The only reading of the charter's `ceiling` column under which every row is consistent. Distinct from `aggregate_mb`, the one **union** number, measured by installing `omniweave[recommended]` into a fresh environment and deduplicating on installed path. |
| Release provenance | concept | The Sigstore bundle, the GitHub build attestation and the SLSA build-level-3 `provenance.intoto.jsonl` that together prove a first-party artefact was built from this repository at this commit by `release.yml`. **Deliberately not called an Attestation**, which the lock reserves for the sha256 over a driver card written by `ow conform` — tamper-evidence for a card and explicitly not a signature. Two words, two guarantees, and conflating them would let a passing conformance run read as a publisher signature. |
| First-party release manifest | concept | `omniweave_core/drivers/first_party.toml`, generated package data listing the thirteen first-party distributions **other than `omniweave-core`** with their version and `dist_sha256`, plus the signed `first-party-<RELEASE>.json` release asset carrying the same content. It is the artefact [the driver system](04-driver-system.md) §4.2 reads to compute `first_party` trust. Generated into `src/` at build time and `.gitignore`d, so a workspace checkout has none and every first-party driver there is `unpinned`. Core's own absence is load-bearing: core is the verifier, so its integrity is a Release-provenance claim rather than a self-witnessed row (§7.2). |
| Approval window | concept | The interval during which a paused `release` environment can still be approved and produce a valid publish, bounded by the **shortest** retention on any artefact the publish job consumes — five days at release 1, set by `slsa-github-generator`'s hardcoded `retention-days: 5` on the provenance file rather than by any omniweave setting. Past it the run is unrecoverable and the remedy is a re-run from the same tag, which is safe only because the build is reproducible (§7.4). |
| Runner class pin | concept | The CI runner label recorded in the workflow beside the per-OS baseline it calibrated, so a runner-image change surfaces as one deliberate re-bless in `eval/BLESS.log` rather than as nine unexplained G10/G26 failures. The reason G10's *hard* assertion is a module count and only its band is wall-clock. |
| Job assertion | concept | An unnumbered `[[job_assertion]]` row in `tools/gates.toml`: a blocking CI check that belongs to one job rather than to the G-series, because it is not a numbered promise any document cites — the distinction that survives `V10-1` dropping the G-series' literal count ([ADR-2](adr/0002-invariant-and-gate-registers.md)). The **nine** at release 1 are `build.reproducible`, `build.wheelhouse_profiles`, `build.first_party_manifest`, `toolchains.reproducible`, `gates.reference_docs`, `gates.workflow_tools_pinned`, `ci-ok.skips_declared`, `gates.invariant_register` and `gates.risk_register`. G27 clause d2 resolves a job-assertion name exactly as it resolves a `G<n>`. |
| `tools/gates.toml` | file | The G-series register: one row per numbered CI gate with its assertion, its implementing script or job step, its owner, its review date, its job, its budget in seconds and its nightly/release schedule, plus the `[[job_assertion]]` rows. Append-only against the previous tag. Distinct from `eval/gates.toml`, which holds the **metric** gates and is owned by [quality](13-quality.md); neither file may name a row the other owns. |
| `tools/invariants.toml` | file | The invariant register, in two table arrays. One `[[family]]` row per invariant prefix — **nine** at release 1: `INV-<n>`, `M-INV-<n>`, `DR<n>`, `RT<n>`, `ST<n>`, `I<n>`, `GR<n>`, `OUT<n>`, `SV<n>` — each naming the document that assigns that prefix's numbers, so a prefix resolves to exactly one series. One `[[inv]]` row per identifier, in the shape [principles](01-principles.md) §1e specifies, carrying its one-line statement, its force, its classes and its named enforcers. Append-only in both: a family is never dropped and an identifier is never renumbered or reused. `gate_docs.py` reads the `[[family]]` rows rather than hardcoding the prefix set. It exists so G27 clause d2 can resolve an invariant identifier a document names, which is otherwise unimplementable. |
| `tools/toolchains.toml` | file | The Toolchain register, in two tables. `[[toolchain]]` rows carry a Toolchain's `name`, `version`, `entry`, `node_range` and the **full sha256 of its platform-independent app bundle**; `[[node]]` rows carry a Node `version`, `platform`, `url` and the sha256 **transcribed from nodejs.org's own `SHASUMS256.txt`**. Two tables because the app is ours and the runtime is not, and because keeping them apart is what stops a platform matrix appearing in a framework that publishes only `py3-none-any` wheels (§3.2). Read by `omniweave_core.toolchain`, which never reads the network. |
| `gate_docs.py` | file | The implementation of G27 clause (d): the five checks of §8.6 — the parser found what it should have found, symbols import, registers contain what a document names (including the spelled-out distribution count against `packages/*`), relative links and `§` cross-references resolve, and `docs_symbols_checked` ratchets. Adopted from graphify's `tests/test_architecture_doc.py`, including its `test_the_table_was_actually_parsed` guard, and widened from symbols to registers, counts and links. |
